# Platform: sign-up, console, app library, reports

## Sign-up and the console

- `workers/platform` + `apps/platform` on the platform's domain (`site.platformDomain`, frcgearbox.com; the gateway sends the bare domain and `www` there). Its D1 (`PLATFORM_DB`) holds the **team registry**: number, name, country, status (`pending` → `active`), founder. The gateway asks it (`GET /teams/:id`, active teams only) before answering a team's addresses. G3ID keeps accounts, sessions, Slack connections and sign-in codes, plus a copy of each team's id/number/name for its foreign keys.
- Sign-up (`/signup`): team details, the terms and that Gearbox is an early open beta (`acceptBeta`, checked by the worker too) → "Add to Slack" (Slack calls back on `<platform>/api/signup/slack/callback`; the platform hands the team and the bot token to G3ID) → a code the founder DMs to the bot. Or "Add to Discord" (`/signup/:id/discord`, calling back on `<platform>/api/signup/discord/callback`): one authorize adds the bot to the founder's server and signs them in; G3ID's `/internal/teams/:id/discord-founder` saves the server and makes the founder the first admin, and the founder lands on G3ID's `/auth/handoff` on the team's own address (a 5-minute one-time token, `lib/handoff.ts`), which sets the cookie there. No code step. A team with no members makes its first Slack sign-up an active admin (`lib/slack-code.ts`), so the founder is its first admin; the platform then marks the team active and sends them to G3ID's `/auth/slack/complete` on the team's own address, which sets the cookie there and opens Portal's `/admin/notifications?welcome=1`: a new team's first step is where notifications go, then its apps. Members join through the team's Slack or Discord. No accounts on other providers are needed.
- **False registrations:** the sign-up form warns that a team found to be falsely registered may be permanently deleted with its data. Anyone can report a number at `/report` (`POST /reports`: team number, email, optional name, message), stored in `number_reports` (at most 20 open per number) for an operator to follow up by email; the operators' console lists them, and every operator is DMed on their own team's Slack (`tellOperators` in `console.ts`: the number and a link to the console, never the reporter's details).
- The platform reaches G3ID through `/api/internal/*` (teams, Slack installations, sign-up codes, Discord founders; for the console: a team's members, accounts by id, delete, hand over), over the service binding only: the gateway never answers `/api/internal`.
- **Operators' console** (roadmap 2.8): `workers/platform/src/console.ts` (`/console/*`) + `apps/platform/src/console/`, at `admin.<platform>` (`CONSOLE_HOSTS`, `consoleUrl()`; the gateway sends it to the platform, for no team). Operators are G3ID accounts listed in the platform's `operators` table, never implied by a team role and never on a kiosk session; they sign in through their own team's G3ID, which may send them back to the console on that team's domain (`sanitizeRedirect`). Console changes must come from a console Origin. Its pages are built like an app's: the shared bar (`AppNavBar` with `team={false}`) and `@g3/ui`'s parts, in the built-in colors. Tools: list teams and number reports, hand a team to another member (`teams.owner_user_id`; they become admin), suspend/reactivate, delete it (all its G3ID accounts, sessions, kiosks, Slack). **Notifications** (`/console/notifications`, `notifications` table, migration `0007`): operators write ones for every team, each a type (`info`: news, downtime and version changes; `critical`: to read at once; migration `0016` made the old `warning` ones `info`), a short description (`summary`, 140 characters) the full text (`body`) and when it expires (`expires_at`, within a year; the page lists Active and Expired); writing and deleting one is logged. **Delivery** (`src/notifications.ts`, migrations `0008` and `0016`, `team_notification_settings`: one row per team, source (`gearbox` or `team`) and type; none = Gearbox's to admins on the home page, the team's own to everyone, no chat): each team's admins choose on Portal's `/admin/notifications` (`GET`/`PUT /team/notification-settings`), separately for Gearbox's and the team's own, who sees each type on the home page (`everyone`, `admins`, `nobody`; shown under the apps from `GET /team/notifications` until it expires) and the one chat channel it's posted in; only Gearbox's Critical ones also take members to DM (`dm_users`, `takesDms`), its active members. **A team's own notifications** (`notifications.team_id`, migration `0016`; null for an operator's): the team's admins write them on the same Portal page (`apps/portal/src/plugins/admin/team-notifications.tsx`; `POST /team/notifications`, `GET /team/notifications/written`, `DELETE /team/notifications/:id`, never a kiosk), and they go by the team's settings for its own (never DMed), to its own home page and chat only, under the writer's name (`deliverToChat` with a team); the console never lists or deletes them. Chat is sent once, when it's written (`deliverToSlack` in `waitUntil`, every active team, through G3ID's `/internal/teams/:id/slack/message` and `/slack/dm-members`, which DMs only the team's active members with Slack linked); changes are in the team's log. The site's team can't be deleted or suspended. Teams are never renumbered: a team's number is its id (`frc<number>`) in every app's data, so a team that claimed the wrong number is deleted and signs up again. Every action, and each look at a team's members, goes in `operator_actions` with the operator's reason; rows older than 12 months are dropped (privacy policy's operator access log). **The team's admins read it** on Portal's Operator Access page (`/admin/operator-access`, from the platform's admin-only `GET /team/operator-access`): opening the member list, handing over ownership and suspending or reactivating, each with when and the reason, never which operator. Reports about the team's number stay with the operators. The console's reason box says the team's admins will see it. The first operator is added by hand (`docs/deploy.md`). **Stats** (`/console/stats`, `GET /console/stats`): teams by status, members (G3ID's `GET /internal/stats`: active, mentors, online now (seen in 5 minutes), active in 7 and 30 days, joined in 30 days, pending) and how many active teams have each app on, counts only and leaving out the demo team. **Visitors** (`/console/visitors`, `GET /console/visits?days=`): the landing page posts `POST /visits` once per browser tab session (`g3_visit_counted` in session storage), and `src/visits.ts` adds it to that UTC day's row in `landing_visits` (migration `0010`), counting it signed in when G3ID's `/auth/me` knows the visitor's session (any team's). Only daily totals are kept, as the privacy draft says.
- **Every team, G3 included, is on the platform's domain** (`<number>-<app>.<platform>`, `<number>.<platform>`). G3 moved there from g3robotics.com, whose app addresses are retired (410). Sign-in providers call back on `id.<platform>` (`signInCallbackApiUrl()`), and the session cookie is set for the domain the request came in on (the platform's, or `gearbox.localhost` in dev). `site.domain` is now only G3's public website and the edge box's tunnel.

## App library (roadmap Phase 4)

- **Subscriptions** are the platform's `team_apps` (migration `0005`): one row per team and app it has switched on or off. Teams that existed before the library were given every app; a new team starts with none. `GET /teams/:id` (what the gateway asks) lists the apps that are on.
- **Switching** (`workers/platform/src/team.ts`, at `/api/team` on the platform, reached from a team's pages as `apiPath("platform")` = `/api/~platform`): `GET /team/apps` (any member: what's on), admin-only `GET /team/library`, `PUT /team/library/:slug { enabled }`, `GET /team/log` (`team_audit_log`), `GET /team/library/:slug/export` (the app's data as a JSON file download, logged as `app_exported`). On runs the app's seed hook (`POST /api/internal/teams/:id/seed`, must be safe to repeat: Skill Tree's default trees, Orders' starter catalog). Off hides it at once and keeps its data 90 days (`delete_after`; the privacy draft's period); switching on within that brings it all back. The platform's daily cron (`clearSwitchedOff`) then calls the app's `DELETE /api/internal/teams/:id` (an app without a delete hook keeps its data). Every on or off DMs each of the team's active admins with a linked Slack (G3ID's `/internal/teams/:id/slack/dm-admins`, from the team's own bot; nothing for a team without Slack). The Apps page offers an app's data as a download before switching it off.
- **Exports:** every app with a delete hook also answers `GET /api/internal/teams/:id/export` with a `TeamExport` (`teamExport` + `exportTeamRows(db, teamId, tables, omit)` from `@g3/auth`: `{ format: "gearbox-team-export", version: 1, app, teamId, tables: { <table>: rows } }`). **Leave secrets out** (Orders' `sac_*` settings, Shop's Onshape keys, Edge's box key hash) and say what's missing in `notes`; Skill Tree exports its tree set file plus progress by skill key; Shop lists its R2 files rather than embedding them. Each app's isolation test runs `checkTeamExport` (A's data, none of B's).
- **The team's log** (`team_audit_log`, migrations `0005` and `0006`): apps switched on, off or deleted, data downloads, and `settings_changed` lines for big settings changes in any app. An app writes one with `logTeamChange(c.env, teamId, { userId, app, what, changed })` from `@g3/auth` (field labels only, never values; `changedFields` and `settingLabels` help, and nothing is logged when nothing changed). It goes to G3ID's `/internal/teams/:id/audit`, which passes it to the platform's `/internal/teams/:id/audit` over G3ID's `PLATFORM` binding; it never fails the change. Logged today: Team Appearance (which parts), Slack connected and disconnected, and each app's team settings (Orders, Pit, Attendance, Shop's Onshape and Slack channels, Edge's data cap, blocking and box key, Scouting's engagement). In tests the G3ID stub records both kinds of call and answers a GET on the same path.
- **The gateway** closes an app that's off: its pages get a "not switched on" page linking the home's `/admin`, its `/api` and `/api/~<app>` a 404 `{ code: "app_not_enabled" }`. It remembers each team's list for a minute. Sign-in, the home and the platform's API are always on; if the platform can't answer, the site's team gets every app.

## Reporting problems

- Plan: `docs/roadmap/issues.md`. Every app's menu (the foot of `AppNavBar`'s drawer) has "Report a problem" (in the bar itself when it has no app list). Anyone else (signed out, on the demo, on a page that's no team's) gets `GitHubReportDialog`: it opens the repository's Problem or Idea form (`.github/ISSUE_TEMPLATE/problem.yml`, `idea.yml`) on GitHub with what they wrote and the page, app and platform versions, browser and team filled in from the address by each field's `id` (text fields only: GitHub doesn't fill dropdowns), so nothing they write goes through Gearbox. A team's signed-in member gets `ReportDialog` in `@g3/ui`, which posts to the platform's `POST /team/reports` (`workers/platform/src/reports.ts`, migration `0012`, `problem_reports`). Each report becomes a **public** issue on midtownrobotics/Gearbox (`GITHUB_REPO`, secret `GITHUB_TOKEN`; unset on staging and in dev, where reports stay in the database): laid out like an issue made with those forms (a `###` heading per field, `issueBody`; change the two together): the text with @mentions broken, the app, the page without its query string, the versions, the browser, the team's number and the sender's **reporter ID** (`reporters`, migration `0013`: a random ID per member, never their account id), and the sender's name only when they turn on "Put my name on it" (`withName`, `reporter_name`, migration `0015`). Operators block a reporter by that ID on the console's Reporters page (`/console/reporters`), without learning who it is; a blocked reporter's reports are refused and unsent ones never go out, and the team's admins are DMed who it is and why. The report form shows members their own ID (`GET /team/reports/reporter`) and that it can be blocked; admins see each member's on their Portal member page and find it with the Members search (`GET /team/reports/reporters`). The hourly cron retries issues GitHub didn't take and DMs the reporter (`sendMemberDM`) when theirs is closed, fixed or not.
- Issues a maintainer labels `ai-ready` are worked on by a daily Claude Code routine following `docs/roadmap/ai-task-prompt.md` (draft pull requests into `staging`, never merging); `.github/ISSUE_TEMPLATE/ai-ready.yml` is the checklist. Change what the task does in that file.

## Demo reset

- **Reset every night at midnight US Eastern** (`workers/platform/src/demo.ts`): the platform's hourly cron (`0 * * * *`) runs it in that hour, or at once when the demo team doesn't exist yet. It calls every app's delete hook, then G3ID's `POST /internal/teams/:id/demo/reset` (its accounts, appearance and sign-in methods; every session ends), then every app's `POST /internal/teams/:id/demo`. Local dev: `curl -X POST http://localhost:8795/api/internal/demo/reset`.

## Docs site (`apps/platform/docs-plugin.ts`)

The docs site, for the admins who set up and run a team's apps, is at `docs.<platform>` (and `/docs` on the platform's own host), served by the platform worker for no team (`DOCS_HOSTS`, `docsUrl(app)` in `@g3/site-config`). Its pages are Markdown in each app's own folder: `apps/<app>/docs/*.md` (one section per app, named by the folder; `apps/platform/docs` is "Getting started", `apps/portal/docs` the team's admin pages), built into HTML at build time by `apps/platform/docs-plugin.ts`. Each file has front matter (`title`, `summary`, `order`, and `pages`); `index.md` is the section's front page. **The docs read in order, from basics to advanced**: Getting started, Portal (the member's own account, then the admin pages), the apps from simplest to most involved (Edge last), and Reference (`apps/platform/docs/reference/`: the setup checklist and troubleshooting) at the end; within an app, its front page, then its setup page, then everyday use, then mentors' work (Orders: its front page is Requests, then Admin, Budget, Vendors, the catalog and New Request, then its bar's order from Approvals to Lists). A page links only to pages before it in that order (the build fails on a link ahead): name a later page in words instead. Links between pages are docs paths (`/orders/setup#share-a-cart`, or `setup` within the section); `team:<app>/<path>` opens that page on the reader's own team. `- [ ]` lists are checklists the reader ticks, kept in their browser. `pnpm --filter @g3/platform test` (and its build) fails on a broken link or heading.

**"Need help?" and each doc's `pages`.** Every doc in an app's folder but `index.md` names the app's pages it's about, as their route paths (`pages: /catalog /request /lists/:id`). Each app's build reads its own docs (`siteConfig()` → `__G3_HELP__`, `packages/site-config/src/help.ts`), and the shared bar's menu has **Need help?** (`helpUrl`) beside the version and Report a problem: it opens the doc naming the page you're on (a `:name` part matches any one part of the address), else the app's `index.md`. The docs build fails when a path isn't a route in `apps/<app>/src` or two docs name the same one. **When a page's address changes or a page is added, update the `pages` of the doc about it in the same PR.**
