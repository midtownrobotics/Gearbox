# G3 Orders (parts ordering)

- **Team-scoped** (roadmap Phase 3): 16 of its 17 tables carry `team_id` (migration `0018`), and every query goes through `inTeam`/`withTeam` (in the tenancy lint). Keys are unique within a team (budget category names, `vendors` by team + key, `app_settings` by team + key, catalog category names, FRCDesign `source_id`s, order-sheet `import_key`s). `lookup_cache` is shared: vendors' public product pages. `test/isolation.test.ts` is its two-team test; `test/teams.test.ts` covers settings, the starter catalog and Slack per team.
- **Each team's settings** (`src/lib/settings.ts`, rows in `app_settings`): currency and fiscal-year start month (G3's rows: USD, July; a new team gets the same defaults), the default sales tax rate (`salesTaxPercent`, 0–100: the tax a new order on the Carts page starts with, as a percent of its items, except at tax-exempt vendors; G3's row is 8.9 from migration `0020_sales_tax.sql`, a new team's is 0), the naming template and whether receiving needs an Inventory place. Mentors edit them on its Admin page (`/admin`; `PUT /settings`); `GET /me` returns currency, start month and the tax rate for every page (the app's `formatCents` uses the team's currency, set from `/me`). There's no team time zone: dates are the viewer's local time. The app sends the browser's zone with every call (`X-Time-Zone`, `localTimeHeaders` in `apps/orders/src/shared/api.ts`), and the worker uses it (`localTimeZone(c)`, `src/lib/local-time.ts`; UTC without one) where it turns moments into dates: fiscal-year boundaries, export dates, imported sheet dates, Share-A-Cart cart titles. Calendar days (need-by, expiries) are stored as 16:00 UTC that day and shown in UTC (`formatDay`), so they're the same day in any zone.
- **The parts catalog is per team.** The FRCDesign parts are kept once under the team id `starter` (migration `0018` made it from G3's catalog, without prices, counts or editors' names); `ensureCatalog` / the `catalogReady` middleware (`src/lib/starter.ts`) copies it to a team in one guarded batch the first time it needs its catalog (`/me`, `/catalog*`, `/suggest`, creating or editing a request). After that the copy is the team's: edits, prices and new parts stay with it. A script-generated catalog fix (`scripts/catalog-*.py`) must update every team's copy and the starter, and only parts still as the starter had them.
- Any member requests one line (vendor link, quantity, budget category, reason). **Only G3ID mentors and site admins** (`is_mentor` or `is_admin`, never kiosk sessions) approve/deny, mark ordered (with actual cost) and manage budget categories. Statuses: requested → approved/denied → ordered → received, or canceled (requester or mentor, before ordering; the stored status value is spelled `cancelled`). **Anyone signed in** (kiosk sessions too) marks an ordered request received: packages are opened by whoever is in the shop.
- `workers/orders` (Hono, Drizzle, D1 `ORDERS_DB`): `/requests` (list, detail with history, create, edit while requested, or by a mentor while approved and not yet ordered: it stays approved, with a `reapproved` event saying what changed, `POST /requests/:id/:action`). The request page's Edit request form also changes the link: a new link is looked up like New Request's (`lookUpDraft`), the requester or mentor chooses to use its name and price or keep theirs, a link new to the catalog asks for a catalog category, and the history keeps what the item was (`replaced`, or `reapproved` with "Was …"), `/categories` (with spent/committed/pending totals), `/lookup?url=` (7-day cache in `lookup_cache`). Status changes are conditional updates on the expected status, and every change is logged in `request_events`.
- Approval sends the requester a DM on their team's own chat, Slack or Discord (`sendMemberDM` with their G3ID user id, through G3ID; nothing is sent if the team has no chat or they haven't linked it), with a link to the team's own Orders address (`src/lib/urls.ts`, through the dev gateway in dev via `LOCAL_GATEWAY_URL`). `requester_slack_id` is no longer written.
- Part lookup goes **straight to the vendor** first, with no edge box (`lookUpAtVendor`, `workers/orders/src/lib/vendor-lookup.ts`): any Shopify store's public Storefront API (`/api/<version>/graphql.json`, `product(handle:)`; a known store's short link such as `andymark.com/am-0028` is followed to its `/products/` page; WCP's Itoris placeholders as below) and REV's product feed (`dashboard.revrobotics.com/feeds/usa/products.json`, kept an hour by Cloudflare; a page's options are its lines, grouped by URL), the approach of VendorDiff (`github.com/tervay/public-vendordiff`). The known vendors are `VENDOR_SITES` (`lib/vendor-sites.ts`, also `@g3/worker-orders/vendor-sites`). Anything else runs **on the edge box** so vendors see the shop connection, not a Workers IP, and only for a team with an edge box: with Edge off (`teamHasApp`), or no box ever set up (the edge worker's `/lookup` answers 503 `code: "no_box"`), Orders answers 422 `code: "no_edge"`, "This vendor isn't supported without an Edge box set up", which New Request shows as a blue note rather than a red error: orders `/lookup` → `EDGE` service binding → edge worker `/lookup` → `agentFetch` → agent `modules/lookup/part-lookup.ts` (Shopify, including the linked products behind Itoris "Dynamic Product Options" dropdowns on placeholder products like WCP's Tube Plugs, BigCommerce, JSON-LD, Amazon, DigiKey API via `EDGE_DIGIKEY_*` in agent.env). The requester's browser headers (User-Agent, Accept-Language, Sec-CH-UA; never cookies) are forwarded for fetches that must look like a browser (Amazon), except that a phone's are swapped for a desktop browser's (Amazon's mobile page lacks the product details; the name also falls back to the mobile title and the page title, and only a real CAPTCHA page is reported as a bot check); Shopify gets an honest user agent because a fake Chrome one gets 429s. McMaster's API is B2B-only, so McMaster links only yield the part number (and name when prerendered). Wire types: `@g3/worker-edge/lookup-types`. Box offline → a lookup the vendor didn't answer fails with 503; requesters can fill details by hand. Orders and Shop call Edge as the member, for their team (`forwardIdentity`), so each team's lookups and prints go to its own box; a team whose box isn't connected gets 503 "isn't connected" (a team with no box at all, `no_box`, above). The agent meters lookup traffic (compressed wire bytes + headers, via `fetch` with `decompress: false`) into the network usage buckets under the pseudo-client `_lookup`; the Network overview shows it as "Part lookups". Usage keys starting with `_` are never LAN clients. Local dev: run the mock agent (`pnpm --filter @g3/edge-agent run dev:mock`) after `pnpm --filter @g3/worker-edge box-key:set -- --local --key local-dev-agent-key` once (stores the mock agent's key, from `mock.env`, as the site team's box key); without it the worker refuses the agent's link and lookups fail with 503 "isn't connected".
- `apps/orders`: plugin-based UI (from `apps/edge`): Requests (`plugins/requests/requests-page.tsx`: a sheet-like table, one grid with subgrid rows so prices and dates are never cut off; sections Pending → Approved → Ordered → Received, then denied/canceled; your own first, then oldest; filters, "only mine" and the search live in the address; `GET /requests` adds `orderedAt` (the vendor order) and `receivedAt` (latest receipt)), New Request (the "why" is optional everywhere; see below), Approvals (mentors; "Replace item" swaps in another link through the same lookup as New Request (`plugins/requests/draft.tsx`), keeping quantity, category, priority, need-by and reason; logged as a `replaced` event with the old item), Carts (`/ordering`, mentors: approved lines grouped by vendor, each card also shown on an approved request's page (`VendorCart`); `POST /requests/order-batch` marks many ordered and splits an optional real order total across them by estimate), Budget.
- Money: only placed vendor orders count against budgets (final qty × price, or an imported line's exact `line_total_cents`, plus the order's fee rows in `order_charges`: Shipping/Tax/Tariff per category; new orders split fees by item cost). `GET /orders/export.csv` writes the team's order-sheet columns; `POST /orders/import` (Budget page, `?dryRun=1` previews) reads the same format back, matching Budget Cat codes to categories and skipping rows imported before (`import_key`).
- Fiscal years start on the 1st of the team's start month at midnight in the viewer's local time (`src/lib/fiscal.ts`, which takes a `FiscalCalendar`: the team's start month and the request's zone; named by starting year: 2026 = "2026–27", or "2026" for a January start). Budgets are per category per year (`category_budgets`); spending counts in the year an order was placed. The Budget page has a year picker and the team's summary table; exports are per year.
- Vendors are matched by lowercased name (`vendors` table holds profiles: tax exemption, shipping thresholds, minimum, lead/shipping days, cutoff, payment, credits in `vendor_credits`). Students only get lead/shipping days (for place-by dates). The Carts page shows profile nudges and marks carts with Blocking or late items "Place today". Requests have `priority` (blocking/high/normal/nice, anyone can set) and `need_by`; place-by = need-by − lead − shipping days.
- Fast entry: New Request takes several links at once; `POST /suggest` returns the templated name (`src/lib/naming.ts`, template in `app_settings`, default `{vendor} {sku} – {title}`), a budget-category guess (last purchase of the same product → vendor default → `category_rules` keywords, whole word) and "bought before" history (same Amazon ASIN / host+path, or same SKU at the vendor). For a part new to the catalog it also guesses the catalog category from light built-in keywords (`src/lib/category-guess.ts`, only categories that exist). Guessed values show an amber "check it's right" hint until the requester changes them. Mentors edit the template and keyword rules on the Admin page.
- Deliveries page (`/receiving`): `GET /orders/receiving` (orders with items on the way + received in the last 14 days), `POST /orders/receive` (anyone signed in), `PATCH /orders/:id/tracking` (mentors). Tracking links guess the carrier from the number.
- One-click carts: Shopify cart permalinks (`apps/orders/src/shared/cart.ts`: `/cart/<variant>:<qty>,…`, variant from `store_variant_id` saved at request time or `?variant=` in the link) and, for Amazon only, Share-A-Cart (`workers/orders/src/lib/share-a-cart.ts`: each team's account connected once on the Admin page over OAuth, kept in the team's settings encrypted with the worker's `SECRETS_KEY` (older plain rows are read and encrypted on first read), calling back on the team's own address; carts saved through their MCP `sac_save_cart` tool). Amazon share links (`a.co`, `amzn.to`) are saved as the product page they redirect to (`expandAmazonLink`, `src/lib/amazon-link.ts`; only the redirect is fetched), and cart building expands any saved before, so the ASIN (`amazonAsin` in `product-key.ts`) is there; the Carts page marks Amazon lines without one. Other stores' Share-A-Cart carts need the browser extension and McMaster's don't work, so REV, McMaster, DigiKey and the rest stay manual.
- **New Request is the catalog** (`/catalog`, the "New Request" tab; `apps/orders/src/plugins/catalog/catalog-page.tsx`): its search box is an omnibox. Words search the catalog; a pasted link opens a request for it right away, filled from its catalog part when the catalog has it (`link-match.ts`, matched like the worker: `@g3/worker-orders/product-key`, shared with `lib/catalog.ts`), else looked up. A part's Request button and "Add a part by hand" open the same request page. `?wishlist=1` (the Wishlist's "Add parts") and `?list=` (a list's "Request parts") carry through. Each part has its own page (`/catalog/items/:id`, `item-page.tsx`: details, last price, Request / Add to wishlist, Edit for catalog editors).
- The request page (`/request`, `plugins/requests/request-page.tsx`): **one** request (or wishlist part) with no search or link box of its own, written with `useRequestComposer` (`request-composer.tsx`: lookup, catalog fill, naming template, category guess, history). `?urls=` / `?catalog=` fill it, nothing gives an empty row; submitting or canceling returns to the page that opened it (`state.from`, a `RequestFrom`), which shows `state.requestMessage` (`RequestDone`) as a banner. Old `/new` links redirect: with `urls`/`catalog` to `/request`, else to `/catalog`.
- **VendorDiff** (`public-vendordiff.vercel.app`, a public tracker of FRC vendors' prices and stock): a catalog part from a vendor it tracks, with a SKU, has a VendorDiff link in its row and on its page (`vendorDiffUrl`: its search for the SKU at that vendor; its own pages are by its own ids).
- Catalog (`/catalog`): anyone logged in browses and requests; only mentors and **trusted students** add and remove categories (`catalog_categories`; `DELETE /catalog/categories` moves the category's parts and families to another one first, in one batch) and add, edit or delete parts (`requireCatalogEditor`). Mentors mark trusted students on the Admin page (`/trusted`; `app_users` lists everyone who has opened G3 Orders, recorded by `GET /me`, which also returns `canEditCatalog`). A part new to the catalog must go in an existing category. `catalog_families` + `catalog_items` (vendor, SKU, `options` JSON of size/type choices, link with `link_kind` product/search/homepage, `product_key` for matching). Seeded once from the FRCDesign library export (`scripts/catalog-seed.py` → migration `0010_catalog_seed.sql`; rows without a link left out), then relinked from each vendor's own product list (`scripts/catalog-relink.py` → `0012_catalog_links.sql`: Shopify `/products.json`, REV's storefront GraphQL, SWYFT's sitemap; matched by part number, pack suffix ignored, then strictly by name; run from a dev machine, not the edge box). Stock material (shafts, tube, spline, extrusion, gear rack) was modeled in the library at a CAD preset length ("1/2\" Hex Lite (1\" L)"); `scripts/catalog-stock-lengths.py` → `0015_catalog_stock_lengths.sql` puts in the vendor's stock length instead (36", 47", 4ft, 480mm), or drops the length when the vendor sells several (AndyMark) or has no listing. Each update applies only while the item is still as seeded. VEXpro parts were dropped: VEX no longer sells the line, and the parts still made are in the catalog under WCP/AndyMark/CTRE. The app loads the whole catalog and searches in the browser (`apps/orders/src/plugins/catalog/search.ts`: MiniSearch, fractions/decimals/thread sizes normalized, typos allowed in words, not numbers). Each part's Request button opens the request page with `?catalog=<id>`. Reusable search box: `CatalogSearch` (`plugins/catalog/catalog-search.tsx`, catalog loaded once and shared via `catalog-data.ts`), used by Replace item. Every submitted request gets `catalog_item_id` (`src/lib/catalog.ts` `catalogItemFor`): the picked item (which takes the requester's product link if it only had a search/homepage link), the item with the same link + Shopify option, or a new item; a link new to the catalog needs a catalog category or the request is rejected. Prices come only from placed orders (`price_cents`/`price_at`); after 7 days a catalog pick is looked up again instead of using the saved price.
- Wishlist (`/wishlist`, `apps/orders/src/plugins/requests/wishlist-page.tsx`, migration `0019_wishlist.sql`): parts the team would like one day, kept in `order_requests` with the status `wishlist` (0019 rebuilt the table: the status CHECK is in its definition). Added through New Request's wishlist mode (`/new?wishlist=1`, `POST /requests` with `wishlist: true`; no list). **Anyone signed in** edits, removes (`DELETE /requests/:id`, only ever a wishlist item, with its history) and promotes one (`POST /requests/:id/promote`: it becomes a request by the promoter, dated now; the history keeps who wished for it). Wishlist items are left out of `GET /requests` (unless `?status=wishlist`), budgets, lists, "bought before" and category guesses; they can't be approved until promoted.
- Lists (`/lists`, `workers/orders/src/routes/lists.ts`, migration `0014_part_lists.sql`): named groups of requests (`part_lists` + `part_list_items`; a request can be on several lists). Anyone logged in makes lists and adds/removes requests; only the creator or a mentor renames, archives or deletes one (requests are never touched). Each list reports counts per status (awaiting approval → approved → ordered → arrived; denied/canceled left out of progress) and cost. Parts get onto a list by `POST /requests` with `listId` (New Request's List picker, preset by `/new?list=`; the Catalog passes `?list=` through to its Request buttons), `POST /lists/:id/items` (Add existing requests), or a request page's Lists card. The list page's fuzzy find (`apps/orders/src/plugins/lists/search.ts`) reuses the catalog's MiniSearch tokenizer, so sizes, typos, SKUs, people and statuses all match.
- Pack quantity (`workers/orders/src/lib/pack-quantity.ts`, migration `0016_pack_quantity.sql`): how many parts one unit of a product is (4 for a pack of 4). Orders counts, prices and budgets what's bought (1 pack); it only matters when parts go to Inventory, which counts parts. `catalog_items.pack_quantity` is what the product is, and each request copies it into `order_requests.pack_quantity` (`packQuantity` on `POST`/`PATCH /requests` and on catalog items; default 1). New Request's "Pack of" field starts from the catalog's, or from a guess read off the product's name (`guessPackQuantity`: "PK4", "10 pack", "box of 50"; `/suggest` returns `packQuantity` and `packQuantityGuess`), shown with the amber "check it's right" hint. A catalog part that's still 1 learns it from a request that says more; after that only catalog editors change it.
- Receiving and Inventory (`workers/orders/src/lib/inventory.ts`): marking parts received can say where they go in the Inventory app (`inventory: { status, locationId?, locations?, robotId?, subsystemId?, quantities? }` on `POST /orders/receive` and `POST /requests/:id/receive`; `locations` is request id → location, `locationId` the place for the rest, and every request needs one or the other). Where each went is kept on the request (`order_requests.inventory_location_id`, migration `0017_inventory_location.sql`). `POST /inventory/defaults { ids }` gives the place each request starts with in the pop-up: with the entry Inventory already has for the part (`from: "entry"`), else where the same catalog part went the last time it was received (`"history"`), else none. Each request goes in as quantity × pack quantity parts, at the unit price over the pack quantity, unless `quantities` says how many arrived. Orders sends them to Inventory's `/intake` over the optional `INVENTORY` service binding, with the person's own session, **before** marking them received, so a failure leaves them on order. `GET /inventory` gives the pages Inventory's places and whether a destination is required: the `inventory_required` row in `app_settings`, off by default, a mentor's toggle on the Admin page (`PUT /settings` takes any of the team's settings, such as `namingTemplate` or `inventoryRequired`). Off and with nothing said, nothing reaches Inventory. The pop-up is `apps/orders/src/shared/receive-dialog.tsx`; it isn't shown when Inventory has no locations and nothing is required. Deploy Inventory's worker before Orders'.
- Lookup errors: the agent answers 422 when a vendor's site blocks or fails (the edge worker passes 400/404/422 on and turns anything else into 502); orders shows "This site isn't supported for automatic lookup".
