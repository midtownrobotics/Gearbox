# G3 Shop

## Teams, Onshape, Slack

- **Shop** (`workers/shop`): `team_id` on all 20 tables (migration `0016`, and every table added since); settings, kiosk presence, Onshape release ids and a release's part numbers are unique within a team. Every query goes through `inTeam`/`withTeam`; "unlock the next step" is `promoteNextSteps` (`src/lib/steps.ts`). **R2:** everything is under `teams/<team>/` (`src/lib/storage.ts`: `drawingKey`, `partFileKey`); `scripts/r2-move-to-team.ts` (`pnpm --filter @g3/worker-shop r2:move-to-team`) copied the site team's pre-teams objects once (`docs/deploy.md`). **Onshape per team** (`src/lib/onshape-config.ts`): each team's API key, secret, company, webhook signing keys and document in its settings, the secrets encrypted with `SECRETS_KEY` (`encryptSecret` in `@g3/auth`); admins save them on Shop's Admin page, which registers the team's webhook at its own `<number>-shop.<platform>/api/onshape/events`. An event's team is the address it came in on (`requestTeamId`), believed only when signed with that team's keys; the BOM queue's messages carry `teamId`. Its job reads the approved release package (`src/lib/onshape-release.ts`, `GET /api/v10/releasepackages/:id`) for the parts, drawings and revisions, and keeps the release's name, notes, who made it, its approvers and comments on `onshape_releases` (migration `0018`); the main assembly's BOM is asked only for quantities, when one is set. Shop's Onshape page (`/onshape`, `apps/shop/src/plugins/onshape/`, from `GET /onshape/releases` in `src/routes/onshape-links.ts`) is one table of the releases and their parts (name, number with revision, quantity). A release's row has its name and when it was released; the name ("Name not found" for a release from before names were kept, never its ID) opens its own page (`/onshape/releases/:id`: its Release ID, comments, and a column each for a part's Part, Drawing and Onshape links at that release's version). Every column sorts: by a release's column (name, released, made by, approved by; ties newest first) each release is listed once with its parts beside it, by a part's column (part, number, quantity) every part is on a line of its own. A part is `obsolete` once a later release holds its part number at another revision (worked out in the route): struck out with an Obsolete badge, and hidden by the Show obsolete parts switch. The sort, search and switch are in the address. Below 768px neither page is a table (`releases-table.tsx`, `NarrowPart` in `release-ui.tsx`), so nothing scrolls sideways: the list is a shaded band per release with its parts under it, or, by a part's column, two lines per part (the part, then its release), with the seven sort buttons above; a release's parts are two lines each, the second its three links in fixed thirds. The site team falls back to the `ONSHAPE_*` worker secrets until it saves its own. **Every call to Onshape goes through `onshapeFetch`** (`src/lib/onshape-api.ts`, with an `OnshapeApi`: db, team and keys; never a bare `fetch` to cad.onshape.com, and a new call adds its kind to `ONSHAPE_CALLS`). It counts the call per team, API key, UTC day and kind (`onshape_api_usage`, migration `0025`) and keeps the last 50 failures (`onshape_api_errors`); times are milliseconds. The key is `keyId` (the start of the access key's SHA-256, never the key), so new keys start their own count: `GET /admin/onshape/usage` is the current keys' calls, `?keys=all` every key's. `GET /onshape/status` (any member) says whether the team has keys and `onshapeProblem`: the current keys' latest call failed with 0, 401, 402, 403, 429 or 5xx and none has worked since (a 404 about one item doesn't count). `OnshapeBanner` (`apps/shop/src/shared/onshape-banner.tsx`) shows either under the bar on every page, kiosks too. The Admin page's Onshape API Usage section (`plugins/admin/onshape-usage.tsx`, `#onshape` opens it) reads `GET /admin/onshape/usage` and has `POST /admin/onshape/check` (one `/users/sessioninfo` call). `test/onshape-usage.test.ts`. **Slack:** release and daily summary posts go to the team's channels on its own Slack (`sendTeamMessage`). Drawings and the part viewer need sign-in. Printing from a team without an edge box answers 503 "no edge box". `test/isolation.test.ts` (D1 and R2) and `test/teams.test.ts` (number-only lists, Onshape keys and webhooks per team, Slack, R2 prefix).

## Batches and files

- A process is `regular`, a **File Producer** (makes a file: CAM, slicing) or a **File Consumer** (uses it: a router, a printer). A part's processes have both kinds or neither, and each File Consumer step comes after a File Producer one (`fileStepError` in `workers/shop/src/lib/process-rules.ts`, shared with the app).
- **A batch** (`staging_batches`, rules in `workers/shop/src/lib/batches.ts`, routes in `routes/staging-batches.ts`) is instances that share one file and move as one unit: through the File Producer process it was made at (`producer_status`), then the File Consumer process its parts go to next (`consumer_process_id`, `consumer_status`). **It is the only thing that links an instance to a file** (migration `0019_batches.sql` turned files assigned straight to instances into batches and dropped `part_instance_files`). A part can also go through a File Producer process on its own, with no batch and no file.
- An instance is in a batch while its step at the batch's File Producer process carries the batch's id (`part_instance_processes.batch_id`). It joins while it is at that process, in no other batch and headed for the same File Consumer process as the batch's others (`stageInto`), and takes on the batch's status there; taken out (`unstageFrom`), it goes back to To Do. Once the batch has finished that process nothing joins or leaves that way: the whole batch is sent back (`sendBatchBack`), or one instance is (`sendInstanceBack`: back to To Do at the File Producer process, with a row in `staging_batch_removals` so the batch still shows it was there).
- **A step a batch moves can't be moved on its own.** The single-part routes (`part-instance-processes.ts`: `/doing`, `/done`, `PATCH`, `/bulk`) refuse or skip a batch's File Producer and File Consumer steps (`governingBatch`, `governedInstances`). A new route that changes a step's status must do the same.
- A batch's name is the one it was given (`name`), else its part and count when it holds one part ("Side Plate × 4"), else "Batch" and its number, counted up within the team (`batchLabel`; the worker sends it as `label`). A batch can be completed without a file. It is deleted only while at its File Producer process. `duplicatePlan` / `duplicateBatch` copy one: the same file and as many of each part as it was made with, from those waiting at the process in no batch.
- **A file is obsolete** once any instance it was made for is (in one of its batches, or sent back out of one), and can't go on another batch (`obsoleteFileIds`). Deleting obsolete instances (Admin) sets `files.obsoleted_at` first, so it stays obsolete.
- In the app, shop data (parts, processes, batches) is one copy shared by the bar, the page and anything opened over it (`shared/use-shop-data.ts`; `refreshShopData()` reloads it for all of them). `shared/batches.ts` reads batches for the pages (which batch moves a part's step, a file's and a drawing's status). A batch's **detail view** is `BatchSheet` (`plugins/batches/batch-sheet.tsx`), a full-screen view like a part's, opened over any page by `?batch=<id>` in the address (`BatchLink`); a batch has no shop view, so kiosks use it too. The Shop Floor shows a batch as one row at its two processes (`producer-process-view.tsx`, `consumer-process-view.tsx`), a part's Files panel lists its batches (`part-files-panel.tsx`), and the Files page groups files (Not Started, In Progress, Complete, Unused, Obsolete) by their batches and drawings by their parts' progress. Names are links, and part numbers stay plain text: a batch's name opens its view, a file's downloads it, a part's opens its page, and a part's name with an instance number opens that instance's details (`plugins/batches/batch-ui.tsx`). Buttons follow the Shop Floor's own: Start, the green Mark as complete (`CompleteButton`), Stage and Unstage, and Send back as a secondary button that asks in a `Dialog`.

## Quality control

- **Shop's Quality Control steps** (`workers/shop/src/lib/quality.ts`, migration `0020`, which also widens `processes.type`): a process whose type is `quality_control` is only marked complete by one of the team's **shop managers** (`shop_managers`, a row per person) or a G3ID admin — every route that finishes a step checks it (`qualityCheckBlock`: the single-instance `done` and `PATCH`, `/part-instance-processes/bulk`, a staging batch's `complete`), so a student can start the step but not sign it off. An admin at a kiosk needs a row too, since a PIN session carries no roles. Only an admin gives a process the type, or takes it away. Admins manage it on Shop's Admin page, Quality Control section (`/admin/quality`: `GET` the team's active members with who's a manager, `PUT /managers/:userId`, `PUT /settings`). **Requiring quality control** (`quality_check_required` and `quality_check_process_id` in `app_settings`) puts one chosen Quality Control process at the end of every part: `withQualityStep` appends it wherever the blueprint is written (creating a part, replacing or reordering its processes), so pages don't have to. Parts already being made keep the steps they have. `/me` tells the pages `isShopManager`, the team's `qualityCheck` and `qualityReports`.
- **Shop's quality reports** (`workers/shop/src/routes/quality-reports.ts`, migrations `0021`–`0023`, `quality_reports`; the `quality_reports_enabled` setting, a toggle in the Quality Control section of the Admin page): with them on, a Quality Control step is finished by a report and no other way (`qualityCheckBlock` refuses the rest), and the shop floor shows one Start Quality Report button there in place of Start Part and Mark as Complete (`QualityReportView`, `apps/shop/src/plugins/board/quality-report-view.tsx`, beside the drawing). Shop managers and admins only. `POST /quality-reports`: the team's checklist answered (`checks`, `[{ label, ok }]` in the team's order, each ticked even when it doesn't apply; refused with 409 if the list changed since the form opened), and when a line fails, the earlier steps it likely came from and/or `unsure`, and notes. A pass finishes the step; a fail leaves the part there (`not_sent_back`) and answers who last finished each earlier step and when (from `actions`). A report keeps the part, step and checklist as they were (names, the labels answered, who did each suspect step and when) with no foreign keys, so it outlives deleted obsolete instances and later edits to the list. `GET /quality-reports` (admins) feeds the Admin page's table (`plugins/admin/quality-reports.tsx`: search, filters, sortable columns, like the Actions Log).
- **The checklist is the team's content** (`workers/shop/src/lib/quality-checklist.ts`, `quality_check_items`, migration `0023`): admins edit it under the reports table, through `GET /admin/quality` (`checklist`) and `PUT /admin/quality/checklist { checklist }` (1–20 lines, no blanks or repeats, replaced whole and logged). No migration holds a team's list: a team gets `STARTER_CHECKLIST` (the four questions the app used to ask) the first time it needs one. `/me` carries it as `qualityChecklist` while reports are on, so the report view renders it.
- **Removing subsystems and processes** (`workers/shop/src/lib/removal.ts`, migration `0024`): only G3ID admins add, remove (`DELETE /subsystems/:id`, `/processes/:id`) and restore (`POST /:id/restore`) them, never a kiosk. One nothing points at is deleted; one that parts, instances, batches or the Actions Log name is archived (`archived_at`) instead. `GET /subsystems` and `/processes` still return archived ones (with `archivedAt`), so what uses one shows its name; pickers for new parts leave them out (`activeOr` in `apps/shop/src/shared/types.ts`), and the worker refuses them for a new part, a new step or the quality check (`removedError`), while a part that already has one keeps it. The required quality check can't be removed while it's required (409). Removals and restores go in the team's log. The Admin page asks with the counts from `GET /subsystems/usage` and `/processes/usage`.
- **What happens to a part that failed** (`openReport` guards every one: the report is still `not_sent_back` and the part still at the check). `POST /quality-reports/:id/send-back { processId, status, fix, fixNote }` sends it to any step the part has, not only one before the check: that step goes to To Do or In Progress and every step after it back to Waiting, so the part is made through each again. With `fix` the note is required and is appended to the **part definition's** `notes` as `Fix for #<instance>: …` (what the shop view shows as Notes, so it's on every instance of that part), and the outcome is `fixed` rather than `sent_back`. `POST /quality-reports/:id/replace` starts over: the instance becomes obsolete (`isStale`, `obsoletedAt`/`obsoletedBy`) and a new one of the same part is added with the blueprint from its first step; the report is claimed before the new part is made, so two taps can't leave two replacements.
- **A fix can add a step to the one part** (sanding a part that failed): a `fix` whose process isn't among the part's steps inserts it into that instance's `part_instance_processes` at the check's index, so it's next and the check stays last (the shift opens the gap through negative indexes, inside the batch's one transaction, so no row collides with one it hasn't moved). The part's blueprint and every other instance are untouched — instances have always kept their own pipelines. Only a `regular` process: a File Producer or Consumer has to be paired across the whole list (`fileStepError`), and a second `quality_control` step would be a second check. The dropdown groups the part's own steps and the ones a fix can add; a plain send back only offers the part's own.

## Release tracker

- **What it is** (`src/lib/release-tracker.ts`, migration `0030`, Admin page's Release Tracker section `apps/shop/src/plugins/admin/release-tracker.tsx`, routes `src/routes/release-tracker.ts` at `/admin/release-tracker`, admins only, in `DEMO_BLOCKED`): an admin links a separate Onshape document (the tracking document; any `/documents/<id>/w/<id>` address, never the team's own document, checked with one call). Shop keeps a copy of each part studio of the team's document in it (`release_tracker_studios`: made, renamed, deleted with the source's), each holding one "Released parts" custom feature per release version and status. The parts come from the version they were last released in (`GET /revisions/d/<doc>`: latest revision per part number; an obsolete one counts as not released), and never-released ones come from the newest version (the main workspace's `parent` from `GET /documents/<doc>`). Solid parts only; sheet metal flat patterns are skipped.
- **The feature's code isn't in this repository.** It lives in Gearbox's public Onshape document. `FEATURE_NAMESPACE` in `src/lib/release-tracker-feature.ts` is a fixed pointer to one version of it (`d…::v…::e…::m…`). To change the feature, make a new version there and update the pointer; each feature's `signature` includes it, so the next sync rewrites them. The feature takes `source` (a part studio reference: `namespace` `d<doc>::v<version>::e<element>::m<element's microversion at that version>`, parts by `deterministicIds`) and `status` (enum `PartStatus`: `UNRELEASED` pink 50% see-through, `NOT_STARTED` gray, `IN_PROGRESS` gold, `COMPLETE` green; the colors are in the FeatureScript).
- **Status** (`src/lib/release-tracker-status.ts`): for the released part number and revision (a definition without a revision counts when none has it), from its live instances' steps: Complete when there are steps and all are done, In progress when any is doing or done, else Not started (also not ingested yet).
- **Syncs are batched to spare Onshape's API allowance.** Anything that could change a color opens a 20-minute window (`openTrackerWindow`: a fixed window per team, `release_trackers.sync_due_at`, one `BOM_QUEUE` message `{ kind: "release-tracker", teamId }` with `delaySeconds`). Releases and new versions (`onshape.model.lifecycle.createversion`, added to the webhook's events; linking the tracker re-registers the webhook) set `refresh`. Step changes come from the `openTrackerAfterChange` middleware in `src/index.ts`: any successful non-GET under `/part-instance-processes`, `/staging-batches`, `/quality-reports`, `/part-instances`, `/part-definitions` or `/admin/obsolete-instances`. A new route elsewhere that changes a step's status must be added there. **Sync now** queues one right away. `runTrackerSync` takes a lock (`sync_started_at`; a busy message retries in 2 minutes).
- **What a sync costs:** reading Onshape (only with `refresh`) is 4 calls: document, all parts at the version (`GET /parts/d/<doc>/v/<version>`), revisions, and the part studios at that version. Add one per release version not seen before; microversions are kept forever in `release_tracker_versions`. The parts read are kept in `release_tracker_parts`, so a window opened only by step changes reads nothing. A feature is written only when its signature differs from `release_tracker_features`; a group that's no longer needed is rewritten in place for a new group, so a part moving on is one call. A sync with no color change makes no calls. Its calls are the `tracker_*` kinds in `ONSHAPE_CALLS`. A copy deleted by hand in Onshape (404) is made again. A sync stops with an error when Shop's Onshape document is no longer the one the tracker was set up on.

## Storage safeguards

- Team-wide capacity policy comes from ID via `teamStorageMode` in `@g3/auth`, with no cached deletion permission. Off/unavailable preserves files and refuses uploads above the hard cap; manual/lifecycle deletion remains separate. Shared quota saves check inside the team lock; Pit logs check start and completion, and assets check before cleanup. Warnings carry the effective mode, retain 90/95/100 deduplication and rearm only after a successful save observes usage below 85%. Rejected requests and policy changes do not rearm alerts.
- Caps: 5 GiB / 10,000 objects per team; 100 MiB per file. At cap, delete oldest first toward 90%, including recent files when older files cannot reach the target. Unknown dates sort last. Orphaned objects count toward quotas and participate in oldest-first cleanup.
- The shared engine uses `deleteOldest` and targets 90% after the incoming save; dates over six calendar months naturally sort before younger files. Incoming/replacement keys stay. Exact object-version approvals remain supported for reviewed operations; no upload route supplies them. Existing manual review/download/delete controls remain.
- Migrations: 0026 (locks), 0027 (notices), 0028 (usage estimate: saves keeping it below 90% skip the lock). Per-team coordination prevents concurrent quota races; cleanup notices, after actual oldest-first/reviewed file deletion, are best effort and batched. See `docs/storage-limits.md`.


- Storage page hooks: own-team `GET /internal/teams/:teamId/storage`, `/storage/download?key=`, and `/storage/archive?eligible=1` serve reports and actual stored files through Platform's authenticated admin API. Internal hooks remain blocked by the gateway. Reports mark all capacity-cleanup candidates, including recent files; no deletion runs on reads/downloads. See `src/lib/storage-report.ts`.
- Usage warning migration `0029_storage_usage_notices.sql`: `notifyStorageUsage` in `@g3/auth` claims 90/95/100 warnings atomically per team/allowance. Below 85% observed on a subsequent save rearms them; cleanup to 90% does not. Actual writes and refused growth report usage without an open page. Cleanup notices remain separate.
