# G3 Inventory

- An **entry** (`items`) is one kind of part: a name, the team's own **fields** (`field_values` JSON by field id) and its **vendor listings** (`item_listings`: one vendor's SKU each; equivalent parts from different vendors are several listings on one entry). Stock is counted per place (`stock`): a **location** in storage, or a location plus the **robot** and **subsystem** it's in use on. One row per entry per place; quantity can't go below zero (a CHECK, which fails the whole batch).
- **Units** (migration `0004_units.sql`, `src/lib/units.ts`, exported as `@g3/worker-inventory/units` and used by Orders too): an entry's `unit` is what one of its quantity is ("ft", "sheet"), `""` for one of each (every entry from before 0004). It's the team's own text: `cleanUnit` trims it, caps it at 20 characters and saves "each"/"ea"/"pcs" as `""`; `formatQuantity` writes "12 ft" (plural only for known words: "3 sheets") and plain "12" for each. Quantities stay whole numbers in every unit (count in a smaller unit for part of one). Anyone who can edit an entry sets it (`POST /items`, `PATCH /items/:id` `unit`; changing it never touches the numbers). Every page shows it after a quantity (`UnitSuffix`, `formatQuantity` in `apps/inventory/src/shared/units.tsx`; cut short with a `title`, so a long one never pushes a phone row sideways), and so does every history line. The unit box (`UnitField`) offers the team's `units` list (Admin page's Units card, `/units`; a plain list like robots, in the setup file as `units`), the units entries already use, then `COMMON_UNITS`. The Locations page counts parts only for entries counted each; "Move all" sums each unit on its own.
- **The arrangement is a team's content, not part of the app.** Fields (`fields`: text, paragraph, number, choice, checkbox, link, date), the tree of locations (`locations`, at most 4 levels: `MAX_DEPTH`), `robots`, `subsystems` and `units` are rows a team makes on its Admin page or loads from a *setup file* (`"format": "gearbox-inventory-setup"`, `workers/inventory/src/lib/setup.ts`; described in `apps/inventory/README.md`). Loading only adds what's missing, matched by name; nothing is changed or removed. A database starts empty; the starter that comes with the app is `workers/inventory/content/starter-setup.json`. **No migration holds any of it and no code names a location, robot or field.**
- **Anyone signed in** (kiosk PIN sessions too) reads everything, adds and edits entries, counts, moves, checks out and in, adds or removes listings, gives a location its title and moves everything in a location. **Mentors and admins** (`requireMentor`) delete, merge and split. **G3ID admins** (`requireAdmin`) use the Admin page.
- `workers/inventory` (Hono, Drizzle, D1 `INVENTORY_DB`): `/inventory` (everything the table shows), `/options` (locations, robots, subsystems), `/items` (`POST`, `GET|PATCH|DELETE /:id`, `POST /:id/stock`, `POST /:id/listings`, `DELETE /:id/listings/:listingId`, `POST /:id/merge`, `POST /:id/split`), `/stock/:id` (`PATCH` quantity = a count, locationId = move; `POST /:id/check-out`, `POST /:id/check-in`), admin `/fields`, `/locations`, `/robots`, `/subsystems`, `/units` (each with `PUT /order`), `/setup` (`export`, `starter`, `preview`, `import`), and `/intake`.
- **Team-scoped** (roadmap Phase 3): all ten tables carry `team_id` (migration `0003`; `units` from `0004`), and every query goes through `inTeam`/`withTeam`, including the stock helpers' subqueries (stock aliases `s`/`t`, which the tenancy lint also checks). The routes take the team from `c.get("teamId")`; `loadItems`, `loadFields`, `loadLocations`, `loadNames` and the stock helpers take it as an argument. Guarded inserts (`INSERT … SELECT … WHERE`) go through `insertWhere` (`src/lib/guarded.ts`). `test/stock-guards.test.ts` covers the guards directly; `test/isolation.test.ts` is its two-team test. Orders sends deliveries with the member's team (`forwardIdentity`).
- Stock changes are one D1 batch each (`src/lib/stock.ts`): take from the row, add at the new place, log the history line, tidy up. Later statements only act if the row taken from still exists, so two people moving the same parts can't both win. An emptied in-use row is deleted, and so is an emptied storage row when the entry has another storage row; an entry's only storage row stays at zero (so an entry with everything on a robot remembers where it's kept) until stock lands in storage somewhere else. The table shows a row per place with parts, or that zero row when there are none. The Check in pop-up is preset to the entry's first storage row (`storageHome` in `apps/inventory/src/shared/stock-dialogs.tsx`), so parts join it; Check out is preset to stay where the parts are.
- Every change to an entry is a line in `item_events` (its History): created, edited, added, counted, moved, checked_out, checked_in, received, linked, unlinked, merged, split. `ref` links a line to an Orders request (`orders:request:<id>`) or another entry (`item:<id>`).
- **Merge** moves the other entry's stock (adding quantities in the same place), listings and history into this one and deletes it. This entry keeps its unit and the other's numbers are added as they are; the merge pop-up says so first when the units differ, and the history line names both. **Split** makes one listing its own entry, with the quantities the mentor says are its, in the same unit.
- **Orders' catalog:** a listing can carry `catalog_item_id` (a part is on one entry at most). Inventory's prices are per part, or per one of the pack's unit: a catalog part that's a pack of 4 for $17.50 shows as $4.38 each, a 100 ft spool for $12 as $0.12 per ft (`partPriceCents`; the catalog part's `packUnit`). Picking a catalog part sold in a unit on Add an entry fills in the entry's unit. The page reads the catalog through `apiPath("orders")` (`apps/inventory/src/shared/catalog.ts`) to show the product page, what was last paid and a Request button; a typed-in listing with the same vendor and SKU, or link, is shown the same way. The worker has no binding to Orders, and a listing keeps its own copy of vendor, SKU, link and price, so Inventory works without it.
- **Location titles and the Locations page:** a location has a `title` (migration `0002_location_titles.sql`): a few words on what's kept there, which pages call its description. Wherever a location is named it reads "name - title" (`labelOf` in `workers/inventory/src/lib/locations.ts` and `apps/inventory/src/shared/places.ts`; Orders' receive pop-up does the same), so history lines say "Dungeon › A1 - Misc. Electronics". The Locations page (`/locations`, `apps/inventory/src/plugins/locations/`) is the table turned round: nested panels that open, each location with what's kept directly in it, a Move button per entry (the whole row) and, under the entries, "Move all" for everything in the location. Each open panel has **Add here**, which opens the Add an entry form (`NewEntryForm` in `plugins/table/new-entry-page.tsx`, the page's own form, `framed={false}`) in a `Dialog` with that location picked; closing it (added or not) puts the focus back on that Add here (`addHereId`), so the next entry is one Enter away. The panels opened or closed by hand and the search live in the page's history entry (`LocationsView`, React Router's location state, replaced as they change), so Back from an entry's page shows the page as it was. A panel's first line is its name, an "Add description" text button and, always at the right, its count; a description shows on its own line under the name, with Edit (the box opens there: Enter or clicking away saves, Escape or Cancel doesn't). `routes/location-contents.ts`: `PUT /locations/:id/title` and `POST /locations/:id/move-contents` (`moveLocationContents` in `lib/stock.ts`: one batch; rows merge with the entry's row already at the new place; the tree itself never changes). Both are for anyone signed in, unlike the tree's own editing on the Admin page.
- **Ordering locations:** on the Admin page, admins drag a location by its handle to put it in order among the ones in the same place (`apps/inventory/src/plugins/settings/locations-card.tsx`, with `@dnd-kit`: one sortable list per place, drops limited to the locations beside the one dragged, and arrow keys that step to the next one beside it). It saves through `PUT /locations/order` with that place's ids in their new order; other places keep theirs. Moving a location into another place is still Edit's job. Use `@dnd-kit` for any other drag-to-reorder list.
- **Received orders:** Orders posts `/intake` (wire types: `@g3/worker-inventory/intake-types`) with the receiving person's session. A delivery finds its entry by listing (catalog id, else vendor + SKU, else link) or becomes a new entry, and is added once per `sourceKey` (`intake_receipts`). A delivery's `unit` (Orders' pack unit) goes on a new entry; an entry Inventory has keeps its own, and its history line says when they differ ("counted ft here"). Each delivery can name its own `locationId`; every place is checked before anything is added. `POST /intake/places` answers where parts that are about to arrive are already kept (the entry's storage row) and the entry's `unit`, changing nothing.
- `apps/inventory`: plugin-based UI (from `apps/skill-tree`): Inventory (`/inventory`: the table; type a quantity to record a count, click a location to move, Check out / Check in pop-ups in `shared/stock-dialogs.tsx`; below 768px each row is two lines instead, like Orders' Requests table: the entry and its Check out / Check in button, then location, quantity and status, without the team's own columns (`NarrowRows` in `plugins/table/table-page.tsx`)), Add an entry (`/new`; `?location=` picks its location to start with, which the table's Add an entry sets from its location filter, and Cancel goes back to the page that opened it, `state.from`), Locations (`/locations`, above), an entry's page (`/items/:id`: details, where it is, vendor listings, history, merge and delete for mentors), Admin (`/admin`, admins). Everything is loaded once and shared (`shared/inventory-data.tsx`), refreshed on focus and every minute.
