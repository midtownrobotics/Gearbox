# Scouting

## Engagement, assignments and deadlines

- Scout assignments count coverage and claim a team in one SQLite statement; valid assignments stay stable and removed teams are replaced before a new report. Both submission checks validate membership in the current lineup. `automaticTbaMatch` accepts the saved current match as a minimum; automatic updates are conditional, forward-only and scoped to the active event. Partial Admin updates preserve omitted event/match settings. Browser countdowns use server time plus `performance.now()`; fresh deadline extensions reopen empty forms without restoring expired answers. Existing reports, rewards and drawings are never rewritten by these corrections.
- In TBA mode, `nextScoutMatch` opens the scout's next form after a report saves, capped at one match ahead of the shared current match. Start timestamps do not gate submission. `/event-context?assign=true` and both submission validations share this selection; the unassigned context and persisted current match stay on the shared live match for Admin. Manual mode remains lead-controlled. The form refresh uses a fresh GET and request ordering so a pre-submit poll cannot restore the previous draft. Assignment requests return 503 on failed or empty schedules; the page retains its last valid draft and keeps editing available while retrying, rather than treating an outage as an assignment change. See [next-match validation](docs/roadmap/scouting-next-match-validation.md).
- Match scouting forms send the `matchKey` of the match they were filled in for, and the report goes to that match: on time while it's the scout's match, or late (`submitted_late`) for the team's `late_window_seconds` after it moved on (`reportMatch` in `workers/scouting/src/index.ts`; migration `0036`). The page keeps drafts on the device (`apps/scouting/src/match-drafts.ts`), never pulls a form with answers away, counts down in a bar before moving on (+30 s up to three times), offers a report that missed the move above the next form to send late, and shows a done screen with the next match after sending (`MatchEntry`, `match-handover.tsx`). Nothing a scout writes is deleted on its own. See [deadline validation](docs/roadmap/scouting-form-deadlines.md).
- Scouting credentials use `teamApiKey` (`workers/scouting/src/api-keys.ts`): saved keys belong to their authenticated team; legacy deployment keys are available only to the original site team. Never return the keys in browser responses or exports.
- Scouting points and match predictions are off by default. Identity admins configure them on Scouting's Admin page; Strategy leads and kiosk PIN sessions cannot change these controls.
- `workers/scouting/src/engagement.ts` reads team-keyed D1 settings. `/scouting/me` includes the settings; `/scouting/engagement-settings` reads them and accepts admin-only PUT updates. Predictions, combined picks and team standings have separate switches, and the points label defaults to "Scout Points".
- The master switch gates `/game`, point awards on scouting submissions, and scheduled prediction result processing. Disabling predictions alone also pauses result processing. Existing balances and picks are preserved; existing combined picks still resolve when predictions resume even if new combinations are disabled.
- Apply migrations through `0035_submission_window.sql` before deploying this code. Existing game table names and API payload keys are retained for compatibility. Engagement settings use the authenticated `teamId`; their routes live in `engagement-routes.ts`. Scheduled prediction processing discovers teams with configured events and processes each team's enabled predictions separately. Scouting is available to every team through the app library; new teams start with points disabled.
- Scouting forms accept zero slider ratings and zero-valued choices as answers. Admin separates the Competition overview from event settings.
- **Analysis's Stats tab is a table of teams** (`apps/scouting/src/AnalysisTeamTable.tsx`, logic in `analysis-table.ts`), Match scouting or Pit scouting, opening on the event being scouted now (`currentEventKey` from `GET /analysis`; the Competition filter changes it). Match scouting: a column per question of the match forms, each team's average of a number and its most-given choice with how often ("No 4/7"); text and drawings show only in its reports. Pit scouting: each team's newest pit report's answers. Every number and choice column sorts. A team's number opens its reports under its row, oldest match first, each labeled with its match (or date, for pit) and scout, with Star and Delete for Strategy leads, then the team's comments. A report linked from Admin opens its team and scrolls to it.
- Automatic match advancing uses TBA timing, independently of Statbotics. Each team's `strategy_event_config.submission_window_seconds` defaults to 120 and accepts whole seconds from 0 to 1800 in Scouting Admin. Migration 0035 converts any saved minute-based value and removes its superseded column. Event context and report linkage use the same selection function in `match-advance.ts`; manual mode uses the lead's selected match instead.
- `workers/scouting/test/engagement.test.ts` covers defaults, admin permissions, API gates, standings visibility and scouting awards.

## Team ownership

Scouting uses Drizzle and the shared inTeam/withTeam helpers for all private tables; the tenancy lint includes it. Migration 0033 preserves old rows under a reserved owner, adopted only by the configured site team before requests. Composite keys and foreign keys include ownership; robot_images.robot_id is the scouted robot, separate from team_id. Predictions/settlement, manual schedules/OCR, roles, engagement and lifecycle hooks are separate modules. New files use teams/<encoded-owner>/; legacy files remain authorized by their owned rows. Platform runs seed, export and D1/R2 deletion through its SCOUTING binding. Deploy the migration and Scouting before the updated Platform manifest. See docs/roadmap/scouting-tenancy.md.

- `pnpm dev` runs the worker with `--local`, so it starts without a Cloudflare sign-in; the `AI` binding (the manual's photo and PDF reading) then doesn't work. Run `pnpm --filter @g3/worker-scouting dev:remote` after `wrangler login` to use it.

## Storage safeguards

- Caps: 2 GiB / 25,000 objects per team; 12 MiB per image and 24 MiB per submission. At cap, only files strictly older than six calendar months are automatically eligible; recent/unknown-date files are protected. Unknown objects count toward quotas and can be removed only when their server upload date is expired.
- The shared engine applies the six-calendar-month UTC cutoff (strict boundary, month-end clamped) and targets 90% after the incoming save. If expired files cannot free enough room, uploads pause. Exact object-version approvals remain supported internally but no route approves younger files and no new approval UI exists. Existing manual review/download/delete controls remain.
- Migrations: 0039 (locks), 0040 (notices), 0041 (usage estimate: saves keeping it below 90% skip the lock). Per-team coordination prevents concurrent quota races; cleanup notices, after actual expired/reviewed file deletion, are best effort and batched. See `docs/storage-limits.md`.


- Storage page hooks: own-team `GET /internal/teams/:teamId/storage`, `/storage/download?key=`, and `/storage/archive?eligible=1` serve reports and actual stored files through Platform's authenticated admin API. Internal hooks remain blocked by the gateway. Reports include six-month eligibility; no deletion runs on reads/downloads. See `src/storage-report.ts`.
- Usage warning migration `0042_storage_usage_notices.sql`: `notifyStorageUsage` in `@g3/auth` claims 90/95/100 warnings atomically per team/allowance. Below 85% observed on a subsequent save rearms them; cleanup to 90% does not. Actual writes and refused growth report usage without an open page. Cleanup notices remain separate.

## Compact field paths

- New report field drawings, drawn auton routes, imported Choreo/PathPlanner routes, and built-in-field local/shared maps store bounded coordinate JSON (`application/vnd.gearbox.field-drawing+json`, `.json` keys) in the existing team R2 prefix. `src/field-drawing.ts` validates field/version, tools, colors, normalized coordinates (with a bounded off-canvas margin to preserve clipping), 128 strokes, 4,096 points and 96 KiB per path; client simplification removes subpixel redundant samples. Paths pin `2026-rebuilt`, never the current season implicitly.
- `src/field-drawing-svg.ts` composes geometry; `src/drawing-storage.ts` embeds the one canonical `apps/scouting/public/field-2026.svg` using Wrangler's Text rule. Existing image URLs render self-contained SVG for vector files and pass old images through unchanged. No server-side PNG conversion, new vendor, migration, or automatic rewrite of old images.
- `apps/scouting/src/FormFieldMap.tsx` keeps coordinate history alongside canvas undo/cancel snapshots, with JSON local drafts; old image drafts remain images until cleared. Keyboard undo is scoped to the focused editor. `VectorFieldMapEditor.tsx` handles new built-in maps; existing/custom-background maps retain `LegacyMapCanvas`. `field-drawing-view.ts` renders local previews against the shared field without saving flattened copies.
- Paths count toward the existing byte/object caps and six-month cleanup. JSON report keys are included in metadata cleanup and friendly storage labels. Single Storage downloads are standalone SVGs; bulk archives retain JSON plus one shared field SVG. The app-data JSON export still contains file references, not these files.
- Dev-only `/preview/drawing` on Scouting's Vite server demonstrates draw/undo/restore and coordinate size; it makes no team requests and is excluded from production. Regression coverage: `test/field-drawing.test.ts` and `test/storage-eviction.test.ts`.
