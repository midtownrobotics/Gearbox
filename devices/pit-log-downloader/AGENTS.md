# Pit log downloader and match logs in Pit

- `devices/pit-log-downloader` (`@g3/pit-log-downloader`, its own version like the edge agent): runs on a pit computer (Linux, Windows or macOS) on plain Node 24 (`pnpm --filter @g3/pit-log-downloader start`, which serves the page each release built; `start:build` builds this code's first). It does nothing until it's paired with its team's Pit (below), which gives it its team. Then, when the computer joins the robot's network (`10.TE.AM.x`, from the paired team's number), it copies AdvantageKit `.wpilog` match logs off the roboRIO over SFTP (node-ssh), names them by match and event, and uploads them to the team's Pit (below) whenever it's online. Its status page (`web/`, on `127.0.0.1:3000`) is React + Vite + Tailwind from `@g3/ui`'s parts, under `AppNavBar` with `team={false}` (no sign-in, no app list): it's a tool on the team's computer, not a team's app. Once paired it takes its team's Team Appearance (colors, names, its avatar online, the tab title): the page's `@g3/ui` loads `/team/ui` from the downloader itself (`VITE_G3ID_API_URL` = `/api/gearbox` in its `vite.config.ts`), whose `GET /api/gearbox/team/ui` asks Pit's `GET /downloader/team-ui` (with its key; Pit asks G3ID's `/team/ui` over its binding with `X-Team-Id`) at most once a minute, keeps the last copy in `DATA_DIR/appearance.json` for offline, and falls back to the team's defaults. Before pairing it's in the built-in colors; pairing and unpairing reload the page. The server (`src/`, Express) answers `/api/status` (its shape is `src/status.ts`, imported by the page) and `/api/download`, and serves the built page (`pageDir()`: `page/`, or `dist/web` while it was built more recently); `watch` runs Vite inside it (`--watch-page`) instead. `--dev` (`start -- --dev`, `watch -- --dev`) pairs with the team's Pit through the dev gateway (`teamAppUrlVia` with the gateway's URL from `.dev-ports.json`: `http://1648-pit.gearbox.localhost:8796`). Moved in from the old Pit-Log-Downloader repository.
- **Match logs in Pit** (roadmap L.3, L.4): the downloader uploads each copied log it hasn't yet (`uploadLog` in `src/gearbox.ts`, one at a time while online, `status.uploaded` in `logs.json`) to Pit's `/downloader/logs` routes (`workers/pit/src/match-logs.ts`, `requireDownloader`): `POST` starts one (answers `exists` when Pit has the same event, name and size), `PUT /:id/parts/:n` sends 10 MiB parts (R2 multipart: Workers refuse request bodies over 100 MB), `POST /:id/complete` stores it. Files are in Shop's R2 bucket (`LOGS` binding, `g3-bucket`) under `pit/teams/<team>/logs/<event>/<name>.wpilog`, outside Shop's own `teams/<team>/`, which Shop deletes when it's switched off; rows in `match_logs` (migration `0014`, one per team, event and name). Pit's Logs page lists them by event (`plugins/logs/match-logs.tsx`, `GET /logs`), downloads (`GET /logs/:id/file`) for anyone signed in and deletes (`DELETE /logs/:id`, `DELETE /logs`) for admins only (`requireAdmin`; `canDelete` in `GET /logs`). Pit's delete hook deletes the files; its export leaves them out. There's no Google Drive any more.
- **Limits** (`MAX_SIZE`, `MAX_LOGS` in `match-logs.ts`): logs are gzipped (level 9) on the downloader and stored gzipped (`.wpilog.gz`; `size` is gzipped, `raw_size` the .wpilog's, `trimmed`, migration `0015`); one over 40 MiB gzipped isn't taken (`too_big`) and waits on the downloader until it's trimmed. A team keeps at most 20: its choice `matchLogsWhenFull` (Pit `settings`, manifest setting, `PUT /logs/settings`, mentors and admins, on the Logs page) is `skip-new` (default: `POST /downloader/logs` answers 409 `full`, and the downloader waits 5 minutes before trying again) or `delete-oldest` (completing an upload deletes the oldest beyond 20). A single log downloads with `Content-Encoding: gzip` (`encodeBody: "manual"`), so the browser saves a plain .wpilog. `GET /logs/export.zip` is every log as one zip of .wpilog files, built by `src/zip.ts` from the gzip files as they are (the deflate data between the gzip header and trailer, whose CRC-32 and size go in the zip's headers: no recompressing or hashing); the Logs page's Export and delete all then asks, once the download has finished, to delete the logs it held (`DELETE /logs { ids }`). The Logs page has a beta note at the top.
- **Trimming** (the downloader, `src/wpilog.ts`): `timeline` reads a .wpilog's bytes per second and the enabled and autonomous spans (AdvantageKit's `/DriverStation/Enabled` and `/Autonomous`), and suggests 15 s before the first enable to 15 s after the last disable; `trim` writes the part kept, every entry still started and its last value before the cut repeated at the start. The status page's Trim dialog (`web/src/trim-dialog.tsx`, `GET`/`POST /api/logs/:id/trim`) charts it with two sliders, a Suggested trim and the size it comes to gzipped; the file on the computer is never cut. Pit's Monitor shows a Logs section while the team has a paired downloader (the downloader's status, then the 3 newest logs), under the stream link's feed (shown only when the link is set); On a wide screen (xl) the Monitor is three columns: Our next match across the left two, and under it the ranking and the match list (first column) and Up next, In the pit now and the stream link's feed (second); batteries, checklists (each on one line in one grid: names as wide as the longest, then bars of the same length filling the rest) and logs in the right (on a narrower one every part is in one column, in an order set by `order`). The Monitor asks Pit's `/health` every second (`plugins/pit-monitor/connection.tsx`): an Online dot with the last answer's time in its header, and after two failed checks in a row a full-screen Offline notice until it answers again, when it reloads at once; a failed refresh keeps each part as it last was.
- **Status in Pit**: the downloader tells Pit what it's doing every 10 s while online (`POST /downloader/status`: on the robot's network, whether the roboRIO answered, logs copying, the one uploading, how many wait), kept on its `log_downloaders` row (`status`, `status_at`, migration `0017`); `GET /downloaders` adds `status` and `online` (said so in the last 45 s). Pit's Logs page (a Log downloader card, asked again every 10 s) and the Monitor's Logs section show one (`shared/downloader-status.tsx`: online first, then the one heard from last). On the downloader, the robot is Connected as soon as the computer is on its network (`10.TE.AM.x`); listing and copying its logs runs beside the 3-second loop (never holding it, or the page), again every 30 s while connected; a copy goes to `<log>.part` and is renamed when whole, and is stopped (the connection closed, tried again at the next check) when the robot's network goes, when it moves no bytes for 30 s, or when SSH keepalives go unanswered (about 15 s); and the Robot tile says when the roboRIO isn't answering. Once a minute it asks Pit which logs it has (`GET /downloader/logs`), so its "In Gearbox" tags follow Pit: one deleted there says Deleted from Gearbox and isn't uploaded again on its own; its Upload again button (`POST /api/logs/:id/upload`, while the file is on the computer and Pit doesn't have it) clears `status.uploaded` and starts the uploader.
- **Pairing with Pit** (roadmap L.2): Pit's Logs page (`apps/pit/src/plugins/logs/`) shows a team with no downloader the setup steps for Windows, macOS and Linux (`setup-steps.tsx`, with the team's `TEAM_NUMBER` and, off the usual address, `PIT_URL` filled in) and lets a mentor or admin get a 6-digit code (`POST /downloaders/codes`, `requireMentor`; one per team, 10 minutes, once, dead after 5 wrong tries). Until it's paired the downloader's status page is only a pairing form (team number, code, the computer's name). It sends them to its own `/api/gearbox/pair`, which posts the code to `POST /downloaders/pair` on that team's Pit address (no session: the team is the address, `requestTeamId`), and gets back a key (`pld_…`) kept with the team number and Pit address in `DATA_DIR/gearbox.json` (mode 600; a saved pairing for another Pit than the one now set, by `PIT_URL` or `--dev`, is ignored, unless its address was typed on the pairing form: Use another Pit address sends `pitUrl` (its origin, `parsePitUrl` in `src/config.ts`), kept with `chosenUrl: true`, and every call after pairing goes to the paired `pitUrl`). Pit keeps only its SHA-256 (`log_downloaders`, `log_downloader_codes`, migration `0013`; `workers/pit/src/downloaders.ts`), lists them for anyone signed in (`GET /downloaders`), and mentors remove one (`DELETE /downloaders/:id`). Routes for the downloader go behind `requireDownloader` (`Authorization: Bearer <key>`, on its own team's address; sets `downloaderId`): `GET`/`DELETE /downloader/me`. The downloader checks its key every minute while online and unpairs itself if Pit removed it; unpaired (by itself, its page or Pit), it stops until it's paired again with a new code. Pit's setup steps add `-- --dev` to the start command on a local Pit and a `PIT_URL` line off the usual address. Its local API refuses a Host that isn't loopback (DNS rebinding) unless `HOST` opens it, and any change that isn't JSON (another site's form). Pairing and codes are in `DEMO_BLOCKED`, and the team's log records pairing and removal.
- Settings are optional, in its gitignored `config.env` (`config.env.example`, read by `src/config.ts`), never in code: data folder, port, host, and `PIT_URL` for a Pit off the team's usual address (staging). There's no `TEAM_NUMBER`: the team comes from pairing. Its data (`logs.json`, `logs/<event>/`) is in `DATA_DIR` (`data/`, gitignored), and each log's local path is worked out from it, never stored. Paths on the roboRIO always use `/`; paths on the computer always go through `node:path`.
- **Installing** (Pit's setup steps, the README): a shallow, blobless, sparse clone of `public` (the released code) with only the downloader and `packages/site-config` (`DOWNLOADER_FOLDERS` in `apps/pit/src/plugins/logs/setup-steps.tsx`; root files come with any sparse checkout), about 2 MB, then `pnpm install --prod` (about 6 MB: no Vite, React or `@g3/ui`); `git pull` updates it. That works because the status page is committed built: `release.yml` runs `build:release` (into `page/`, tracked, `linguist-generated` and `-diff` in `.gitattributes`, skipped by Biome) in each release commit, so `page/` exists only on `public` and on `staging` after a release is merged back. The server must only need its `dependencies`. `.github/workflows/pit-log-downloader.yml` builds the page like a release, then switches to those folders and a `--prod` install before the smoke test, so a new package it needs to run fails there: add it to the setup steps, the README and the workflow.
- `ssh2`'s native add-ons are off (`allowBuilds` in `pnpm-workspace.yaml`), so it installs without a compiler. `pnpm --filter @g3/pit-log-downloader smoke` starts it and checks its status page; `.github/workflows/pit-log-downloader.yml` runs that on all three systems.
