## Quick Start

**Install & Develop:**
```bash
pnpm install
pnpm dev              # Start all apps and workers in parallel
pnpm typecheck        # Type check all packages
pnpm lint            # Run Biome linting and formatting
```

**Commit Quality:**
```bash
pnpm biome check --write   # Fix formatting/linting before commit
pnpm -r --if-present typecheck  # Ensure no type errors
```

## Platform Roadmap (read this first)

These apps are being turned from one team's tools into a hosted platform that many teams share. The plan of record is `docs/roadmap/roadmap.md`. **Before changing code, read its Progress section and the phase your change touches**, so the change moves toward the plan instead of away from it.

**Rules that follow from the roadmap:**
- **No new team-specific values in code, config or migrations**: team name, number, domain, Slack channel IDs, time zone, currency, event keys. Read them from `@g3/site-config` (see "Site config" below), which becomes per-team data in Phase 2.
- **No fixed colors for content.** A team's colors come from Team Appearance, so everything a page shows uses them: `primary-*` for the team's color, `secondary-*` for grays, `bg-surface` for cards, `bg-page`, `bg-inset` and `border-line` (in plain CSS, the `--g3-*` variables). Text on a fill in the team's color is `text-on-primary` (plain CSS: `var(--g3-on-brand)`), never `text-white`: a team chooses light or dark text for its color. Don't write a hex value, `bg-white`, or a Tailwind color such as `red` or `blue` as an accent. A fixed color is only for meaning: red for an error or deleting, green for done, amber for a warning, a status badge. See "Editable team appearance" and "Color Implementation".
- **Page text is short and about what the user does.** A description, hint or empty state says what the user can do or needs to know, in a sentence or two. Leave out how it works underneath (storage, caches, endpoints, what the code does), what changed, and what users can see for themselves. Keep warnings about consequences (it can't be undone, who can see it) and steps an admin has to follow.
- **US English spelling everywhere**: page text, docs, comments and names in code (color, gray, canceled, labeled, recognize, center). The one exception is a value that's already stored: Orders' request status is `cancelled` in the database and the API, while pages show "Canceled".
- **No new single-team assumptions in schemas**: no `CHECK (id = 1)` settings rows, and no key that is unique across the whole table when it should be unique per team (a vendor key, a setting name, a PIN). New tables for a team's data should be easy to scope with a `team_id` later (Phase 3).
- **Sign-in and roles only through `@g3/auth`**. App workers don't read the session cookie themselves; in Phase 2 a gateway hands them the user and team.
- **Core apps must not depend on Edge.** Edge is an optional app any team can run with its own box (roadmap section "Edge: an app any team can run"). Orders part lookup and Shop printing treat it as an optional provider and must keep working (by hand) without it.
- **Hosting and deploy changes need the owners' yes first**: a new Cloudflare product, a paid add-on, a new vendor or a new domain. The roadmap's "Hosting and stack decisions" section lists what is already confirmed; ask before going beyond it.
- **Features that change what data is collected, how long it's kept or who can see it** must match the drafts in `docs/legal/` (Terms of Service, Privacy Policy). Update the draft in the same PR, or say in the PR that it needs a decision.

**Keep the roadmap current.** When a change completes or advances a step, update `docs/roadmap/roadmap.md` in the same PR: the step's Status, the Progress table, and a row in "What landed". If a change makes part of the plan wrong, fix the plan there and say so in the PR description. A roadmap-only change takes an empty changeset.

## UI Alignment (read before changing a page)

The apps are being brought into one design language. The plan of record is `docs/roadmap/ui-alignment.md`: the decisions, the rules a page follows, each step's status and what each app still needs. **Read it before changing how a page looks or behaves**, and update its Progress table in the same PR as a step.

**Rules that follow from it:**
- **Build pages from the shared parts in `@g3/ui`** (`packages/ui/src/components/`): `Page` (title, `description`, `actions`, `width`), `PageLoading`, `Card`, `Stat`, `Button` (`primary`, `secondary`, `danger`; `size` `sm` or `lg`) and `buttonClass` for a link that looks like one, `ConfirmButton` and `ConfirmQuestion`, `Field` with `inputClass`, `TextField` (below), `ErrorBanner`, `SuccessBanner`, `Loading`, `Dialog`, `Toggle` and `Switch`, `Chip`, `Badge` with `tones`, `ProgressBar`, `focusRing`. Orders, Inventory, Skill Tree, Edge, ID, Portal, Pit and Shop are built from them; Scouting now uses the shared page frame, cards and standard controls, with its specialized drawing and touch layouts below shared styles in the CSS cascade. Its pages have React Router addresses; multi-step questions use `QuestionProvider` / `useQuestions` and the shared `Dialog`. Don't add an app's own copy of one: a part two apps need goes in `@g3/ui`. Tailwind finds their classes through `@source "./components"` in `packages/ui/src/index.css`.
- **Red means a problem, in every app**: an error, a delete or danger button, a "no" status, an overdue or over-budget mark (`ErrorBanner`, `Button variant="danger"`, `tones.danger`, `text-red-700`). The team's color (`primary-*`) never stands for one, since a team can choose any color.
- **An app opens on its most-used page**, the first in its bar. No page exists only to list other pages. A summary page is called Overview. **An address that isn't a page goes to the app's home** (a `path="*"` route to `/`; Scouting checks its own paths), never a blank page.
- **An app's settings page is called Admin** and is last in the bar. A page's title is its bar label.
- **Ask in the page** (`ConfirmButton`, a `Dialog`), never with `window.confirm`, `window.prompt` or `alert`.
- **Every text box is `TextField`** from `@g3/ui` (an input, or a textarea with `multiline`; it takes the element's own props), never a plain text `<input>` or `<textarea>`: `pnpm lint:text-fields` (CI) fails on one. `variant`: `default` (the `inputClass` look), `compact`, `inline`, `search`, `plain` (only your `className`). Give it a `kind` (`partName`, `reason`, `note`, `url`, …: the lists in `packages/demo/src/safe-text.ts`; add one there if none fits), which picks the safe text the public demo offers in its place, or `typeable` for a box that only filters the page or holds a number, price or color. A search box (`type="search"` or `variant="search"`) must only filter what the page already has.
- **"Sign in" and "Sign out"**, not "Log in" or "Log Out". A chosen filter chip is near-black, not the team's color.
- **A signed-out visitor goes straight to sign in**, in every app: the moment the app knows nobody is signed in (its `/me`, or any call, answers 401), it calls `redirectToSignIn()` from `@g3/ui` (`packages/ui/src/sign-in.ts`: the team's ID sign-in page, coming back to the page they were on). No app shows a "Sign in" page of its own, except the team's front door: Portal's home, signed out, shows the team's number and name with Sign in and Sign up (ID's `/signup`), then "Not a team member? Visit the team's public site" (when it has one) and "Not team N? Find your team" (`PublicSiteLink` and `NotYourTeam` from `@g3/ui`, also under ID's sign-in pages) (`FrontDoor` in `apps/portal/src/plugins/home/home-page.tsx`); Portal's admin pages redirect like any app. An app that keeps working offline (Pit, Scouting) only does it on a 401, never because a call failed. ID's sign-in pages have the team's public site link and "Not team N? Find your team" (the platform's `/team`).
- **The sign-in app is called "ID"** in text ("your ID account"), and "G3 ID" as its wordmark and tab title, like any app. It isn't "G3ID".

## Repository Structure

**Monorepo using pnpm workspaces:**

- `apps/` — React frontends (g3id, portal, shop, pit, skill-tree, attendance, scouting, edge, orders, inventory, schedule, platform)
- `workers/` — Cloudflare Workers: one per app (g3id, portal, shop, pit, skill-tree, attendance, scouting, edge, orders, inventory, schedule, platform), each serving its app's page and its API at `/api`, plus `gateway`, which routes `*.<domain>` to them
- `packages/` — Shared libraries (auth, ui, slack, discord, demo: the public demo's people, safe text and guard)
- `devices/` — Software that runs on physical hardware (edge-agent: Bun, compiled to an arm64 binary; pit-log-downloader: Node 24, below)
- `infra/edge/` — Hand-applied system config for the shop edge box

## Architecture Overview

### Core Stack
- **Backend**: Hono (routing), Drizzle ORM (database), Cloudflare Workers (serverless)
- **Frontend**: React, React Router, Tailwind CSS v4
- **Database**: Cloudflare D1 (SQLite-compatible)
- **Storage**: Cloudflare KV (sessions, rate limiting)
- **Auth**: the team's chat, Slack or Discord (primary), Google, GitHub, Steam, Email (local), PIN (kiosk)

### Key Systems

**G3ID Authentication Worker** (`workers/g3id/`)
- RESTful routes at `/auth/*` for login flows
- Slack integration at `/slack/*` for commands and events
- PIN authentication at `/auth/pin` for kiosk devices
- Admin routes at `/admin/*` (user management, kiosk device management)
- Database schema in `src/db/schema.ts` with migrations in `src/db/migrations/`
- Session management: OAuth sessions stored in KV with D1 backup, PIN sessions in D1 only
- **Important**: PIN sessions cannot access admin routes (enforced in `middleware/auth.ts`)
- Deleting a user (`DELETE /admin/users/:id`) removes the account and everything that points at it (sign-ins, sessions, kiosk PIN, sign-in and activation codes, old merged-in shells) in one batch, so it's all or nothing; the team's kiosks pass to the admin doing it, and its Slack connection stays. A new table that points at `core_users` must be handled there. An admin can't delete their own account

**G3ID Web App** (`apps/g3id/`)
- Plugin-based architecture: each feature is a plugin with routes and nav items
- Color system centralized in `packages/ui/src/index.css` using Tailwind v4 `@theme` block
- Primary color: #A32035 (burgundy), Secondary: neutral grays (#f8f8f8–#1a1a1a)
- Navbar updates auth state on every route change (useLocation dependency)
- **ID only signs people in** (decided 15 October): its pages are sign-in (providers, email, the Slack code), sign-up and pending approval, `/demo`, and kiosk activation, PIN sign-in and removal. The account page and the admin pages for members and kiosks are on Portal (below); ID's old addresses redirect there (`Moved` in `shared/moved.tsx`: `/` and `/dashboard`, `/admin/users`, `/admin/users/:id`, `/admin/kiosk`). After a sign-in with nowhere else to go, the worker sends people to Portal's home; after linking a sign-in, to Portal's `/account`. ID isn't a tile on Portal or in the All Apps menu.
- The Members list (Portal's `/admin/members`, `apps/portal/src/plugins/admin/members-page.tsx`, from ID's `GET /admin/users` through `/api/~id`) opens on the Active tab and is searched (name, email and the account names people sign in with: `providerEmail` on each identity, `matchesSearch` in `members-shared.tsx`), sorted (join date, name, last login; never-logged-in last) and filtered (status tabs, role, sign-in provider) in the page, from the one `GET /admin/users` load; the tab, search and filters are in the address. Clicking someone opens their page (`/admin/users/:id`, `admin-user-page.tsx`, from `GET /admin/users/:id`: their sign-ins with account names, whether they have a kiosk PIN (never the PIN), and approve, roles and delete, which asks in the page)

**Attendance Worker** (`workers/attendance/`)
- Attendance members, sessions, manual adjustments, and yearly totals live in its own Cloudflare D1 database, bound as `ATTENDANCE_DB`. Team-scoped (roadmap Phase 3): every table has `team_id` (migration `0002`), and every query goes through `AttendanceDb(d1, teamId)` (`src/db.ts`, Drizzle with `inTeam`/`withTeam`; schema in `src/db/schema.ts`).
- Each team's settings (`attendance_settings`, `src/settings.ts`): when its school year starts and the auto sign-out limit (a session still open after it is closed and doesn't count). G3's row keeps 3 August and 12 hours; a team without a row gets 1 August and 12 hours. Admins edit them on Attendance's Admin page (`apps/attendance/src/plugins/admin/admin-page.tsx`) through `GET`/`PUT /admin/settings`. The cron closes stale sessions team by team (`teamsWithOpenSessions`, the lint's one `// tenancy: all teams` exception).
- G3ID provides session identity; the leaderboard lists the team's active members (`activeMembers`).
- **Attendance is its own app** (`apps/attendance`, decided 15 October; it used to live on G3ID's pages): a plugin-based UI with the shared bar. Leaderboard (first, for everyone), My Attendance (everyone), QR Codes and Admin (admins). The QR code displays (`/kiosk`, `/signin`, `/signout`, `src/kiosk/`) and the confirm page members reach by scanning (`/?action=…&w=…`) are full screen, with no bar. G3ID's old `/leaderboard` and `/admin/attendance` redirect here (`Moved` in `apps/g3id/src/shared/moved.tsx`). Portal has an Attendance tile and the All Apps drawer lists it (`portalAppLabels`).
- **The Leaderboard page, for every member** (`apps/attendance/src/plugins/leaderboard/`): `GET /report` is for anyone signed in and covers the leaderboard's people (`leaderboardMembers`: the team's active members, each once under the name they have now). It returns every sign-in and adjustment of the current school year with what it counted for (`countSession` in `src/index.ts`, the one set of rules the summary shares: `completed`, `open` (time so far), `missed` (no sign-out: no hours) and `adjustment`), each by its member's index, and each member's `isMentor`. The worker doesn't work out days: the page groups sign-ins by the viewer's local day (`attendance-report.ts`), since a team has no time zone. A meeting day is a day anyone shown signed in, and a missed sign-out counts as attending it. The page is the reports (`attendance-reports.tsx`, plain HTML and SVG), with no separate ranked list: a grid of members (name, hours, meetings attended) by meeting days, its rows sorted by any of those three from their column names (most hours first to start; `sortRows`), with five shades of green by hours scaled to the team's own days, a green ring for someone signed in now and a red ring for a missed sign-out; how many signed in each day; everyone's hours over time with the six highest named; a Students only switch (mentors left out) and a CSV download. `GET /leaderboard` is still served, but no page uses it. Chart colors are fixed, one set per theme, checked against that theme's card (`.att-report` in `apps/attendance/src/index.css`).
- **My Attendance** (`/me`, `plugins/me/`): the signed-in member's own school year from the same `GET /report` (`mySummary` in `my-attendance.ts`, matched by G3ID user id): hours against the team's average, place on the Leaderboard, meetings attended of meeting days, hours per meeting, meeting days in a row, the last 30 days, missed sign-outs, and every visit and adjustment, newest first.
- **QR Codes** (admins, `/qr-codes`): the three displays with their addresses and how to set up a shop screen. A display asks `GET /code` (admins only) at each 30-second window. When it can't (`kiosk/KioskPage.tsx`: no connection, a server error, signed out, not an admin), it tries again every 5 seconds and at once when the network comes back, says what's wrong in place of the countdown, and keeps the last code up, saying it still works, only while that's true: for 90 seconds (the worker takes a code for about 2 minutes) and never after a server error. Otherwise the codes go and the error fills the screen. The display fills the screen and never scrolls: each QR is the largest square that fits (container query units in `KioskPage.css`).
- **Attendance's Admin page** (admins; `/admin`, `plugins/admin/admin-page.tsx` and `admin-tools.tsx`), from `GET /admin/summary`: who is signed in now, each with Sign out, and Sign Out All (`POST /admin/signout-all`: each gets the time they've had so far); Manage a member (add or subtract hours, remove); and the school year and sign-out limit. New buttons that need a yes ask in the page, not with `window.confirm`.
- Attendance's pages use the shared theme (`@g3/ui/index.css`, Tailwind): the QR code displays are always dark (also set before first paint in `index.html`) (`forceTheme("dark")` from `@g3/ui`), the confirm page members see follows the shared light/dark setting. Sign-in is green and sign-out red (`--att-signin`/`--att-signout`); the QR codes are dark on a white tile.
- The schema is in `src/db/migrations/`. Apply migrations and import existing attendance records before deploying a worker that reads D1. Production D1 is `g3-attendance-prod`.
- Run `pnpm --filter @g3/worker-attendance test` for Cloudflare runtime tests against a local migrated D1 database.

### Optional Scouting engagement

- Scout assignments count coverage and claim a team in one SQLite statement; valid assignments stay stable and removed teams are replaced before a new report. Both submission checks validate membership in the current lineup. `automaticTbaMatch` accepts the saved current match as a minimum; automatic updates are conditional, forward-only and scoped to the active event. Partial Admin updates preserve omitted event/match settings. Browser countdowns use server time plus `performance.now()`; fresh deadline extensions reopen empty forms without restoring expired answers. Existing reports, rewards and drawings are never rewritten by these corrections.
- In TBA mode, `nextScoutMatch` opens the scout's next form after a report saves, capped at one match ahead of the shared current match. Start timestamps do not gate submission. `/event-context?assign=true` and both submission validations share this selection; the unassigned context and persisted current match stay on the shared live match for Admin. Manual mode remains lead-controlled. The form refresh uses a fresh GET and request ordering so a pre-submit poll cannot restore the previous draft. Assignment requests return 503 on failed or empty schedules; the page retains its last valid draft and keeps editing available while retrying, rather than treating an outage as an assignment change. See [next-match validation](docs/roadmap/scouting-next-match-validation.md).
- Match scouting forms send the `matchKey` of the match they were filled in for, and the report goes to that match: on time while it's the scout's match, or late (`submitted_late`) for the team's `late_window_seconds` after it moved on (`reportMatch` in `workers/scouting/src/index.ts`; migration `0036`). The page keeps drafts on the device (`apps/scouting/src/match-drafts.ts`), never pulls a form with answers away, counts down in a bar before moving on (+30 s up to three times), offers a report that missed the move above the next form to send late, and shows a done screen with the next match after sending (`MatchEntry`, `match-handover.tsx`). Nothing a scout writes is deleted on its own. See [deadline validation](docs/roadmap/scouting-form-deadlines.md).
- Scouting credentials use `teamApiKey` (`workers/scouting/src/api-keys.ts`): saved keys belong to their authenticated team; legacy deployment keys are available only to the original site team. Never return the keys in browser responses or exports.
- Scouting points and match predictions are off by default. Identity admins configure them on Scouting's Admin page; Strategy leads and kiosk PIN sessions cannot change these controls.
- `workers/scouting/src/engagement.ts` reads team-keyed D1 settings. `/scouting/me` includes the settings; `/scouting/engagement-settings` reads them and accepts admin-only PUT updates. Predictions, combined picks and team standings have separate switches, and the points label defaults to "Scout Points".
- The master switch gates `/game`, point awards on scouting submissions, and scheduled prediction result processing. Disabling predictions alone also pauses result processing. Existing balances and picks are preserved; existing combined picks still resolve when predictions resume even if new combinations are disabled.
- Apply migrations through `0035_submission_window.sql` before deploying this code. Existing game table names and API payload keys are retained for compatibility. Engagement settings use the authenticated `teamId`; their routes live in `engagement-routes.ts`. Scheduled prediction processing discovers teams with configured events and processes each team's enabled predictions separately. Scouting is available to every team through the app library; new teams start with points disabled.
- Scouting forms accept zero slider ratings and zero-valued choices as answers. Admin separates the Competition overview from event settings.
- **Analysis's Stats tab is a table of teams** (`apps/scouting/src/AnalysisTeamTable.tsx`, logic in `analysis-table.ts`), Match scouting or Pit scouting, opening on the event being scouted now (`currentEventKey` from `GET /analysis`; the Competition filter changes it). Match scouting: a column per question of the match forms, each team's average of a number and its most-given choice with how often ("No 4/7"); text and drawings show only in its reports. Pit scouting: each team's newest pit report's answers. Every number and choice column sorts. A team's number opens its reports under its row, oldest match first, each labeled with its match (or date, for pit) and scout, with Star and Delete for Strategy leads, then the team's comments. A report linked from Admin opens its team and scrolls to it.
- Automatic match advancing uses TBA timing, independently of Statbotics. Each team's `strategy_event_config.submission_window_seconds` defaults to 120 and accepts whole seconds from 0 to 1800 in Scouting Admin. Migration 0035 converts any saved minute-based value and removes its superseded column. Event context and report linkage use the same selection function in `match-advance.ts`; manual mode uses the lead's selected match instead.
- **Playoff Scouting** (`/playoffs`, `apps/scouting/src/Playoffs.tsx`; worker `src/playoffs.ts`, brackets in `src/playoff-bracket.ts`, migration `0037`): Strategy leads and admins (`isStrategyAdmin`) set up a session (event, bracket: FRC's 8- or 4-alliance double elimination, alliances filled from The Blue Alliance's `/alliances`, a photo scan through Workers AI that shares the schedule scan's hourly allowance, or by hand; up to four teams each, the fourth a backup), choose how scouts get slots (`claim`, `auto`: whole alliances first, fewest-scouted first, our own alliance left out when `skip_own`; or `admin`), start it, start each match and pick its winner, which fills the bracket (`resolveBracket`; only winners are stored, in `playoff_matches`). Undoing a winner is refused once a match fed by it has started. A slot is `red:overall`, `blue:overall` or `<side>:<team>` of the match's lineup (its first three robots unless a lead changed it), claimed in one guarded batch (`takeSlot`). Reports are taken only from the slot's holder, for the last match started: a match's forms close when the next one starts. The team's questions (`playoff_forms`, `STARTER_FIELDS` until a team saves its own, each asked about a robot, the whole alliance or both) stay from event to event. One session being set up or running per team (a partial unique index); others wait with "hasn't started". Everyone signed in reads every live or finished session's answers in the Data view (`GET /playoffs/sessions/:id`), by alliance or by match. `test/playoffs.test.ts`.

### G3 Edge (shop network box)

Design brief: `docs/edge.md`. On-site Orange Pi 5 (hostname `orangepi5`, login user `g3`) routes the shop LAN through a 50 GB/month cellular hotspot.
- `devices/edge-agent` (Bun + Hono, binds 127.0.0.1): `src/core/*` + feature modules in `src/modules/<name>/`. The network module reads nftables `inet acct` counters every 5 min, attributes bytes by MAC, buffers in local SQLite, and pushes to the worker. Per-site stats: `flows_dl`/`flows_ul` nft sets (client . remote IP) plus the dnsmasq query log (`/run/g3-edge-dns/queries.log`) map bytes to domains; hourly top-20 sites per device are pushed. The agent deletes idle entries from the flows sets (its only write to `inet acct`).
- `workers/edge`: **team-scoped, one box per team** (roadmap Phase 3, E.1/E.2): every table carries `team_id` (migration `0005`; `edge_status` and `net_settings` are one row per team, usage/site/client keys include the team, since `_wan`/`_lookup` are the same key on every box), and every query goes through `inTeam`/`withTeam` (in the tenancy lint). `/agent/*` routes take the **team's box key** (`Authorization: Bearer`), on the team's own address (`requireAgent`/`requireAgentKey` in `src/middleware/auth.ts`: the gateway's team, and the key's SHA-256 must be that team's row in `edge_boxes`, `src/lib/box-key.ts`). Admins make the key on the Edge Box page (`POST /box/key`, shown once; a new key replaces the old and disconnects the box). UI routes use G3ID (`isAdmin` required for writes). Modules live in `src/modules/<name>/`. The daily cron (`networkScheduled`) goes team by team (the one `tenancy: all teams` query finds them): 5-min usage into hourly rows after 14 days, site hours into days after 30. **Local time is the box's:** the agent sends its zone (`X-G3-Agent-Time-Zone`), stored in `edge_status.time_zone` (UTC until it has), and billing cycles, daily charts, "today" grants and daily site buckets (its standard time) use it (`src/lib/time.ts` takes the zone; `/me` gives it to the app). A new team's settings start with no cap (`cap_bytes` 0) and cycles from the 1st. `test/isolation.test.ts` and `test/teams.test.ts` (keys per team, link per team, local time, rollups).
- `apps/edge`: plugin-based UI; nav items are grouped by module.
- Agent and app both use Hono RPC types from `@g3/worker-edge` (no shared schema package).
- **Who's online:** the network module also tracks presence from the LAN's neighbor (ARP) table (`modules/network/presence.ts`): every 30 s it sends each known address (leases + table) an empty UDP datagram so the kernel ARPs it, and a MAC that was REACHABLE in the last 2 minutes counts as online, so printers and other LAN-only devices show up too. The Clients page asks live on each load: worker `GET /network/clients` (and `/clients/:mac`) → `agentFetch("/network/presence")` over the link → `{ online }` per client, and it upserts online devices into `net_clients`. Box unreachable → the list still loads with `online: null` and a note. Wire types: `@g3/worker-edge/presence-types`. The Edge Box page's Addresses card reads the box's own LAN/WAN addresses the same way (worker `GET /status/interfaces` → agent `GET /network/interfaces`, `ip -j addr`; `@g3/worker-edge/interface-types`). Its public address is stored, not live: `requireAgent` records `CF-Connecting-IP` from each agent upload in `edge_status.public_ip` (+ `public_ip_since`, when it last changed; migration `0004`).
- **Date ranges and insights:** every Network page (Overview, a device, Sites, a site, a device's sites) takes `?from=YYYY-MM-DD&to=YYYY-MM-DD` (local days of the box; none = the billing cycle; at most 400 days), read by `rangeOf` and declared by `rangeQuery` (`modules/network/range.ts`). Each answers its `range` and `usageStats`: total, average day (over the days that have started), busiest and quietest days, average per weekday, and average per hour of the day (from hourly rows; not for sites, whose hours are kept 30 days). The cap and its projection stay the cycle's. In the app the range lives in the page's address (`useRange`, `RangePicker` in `apps/edge/src/plugins/network/range.tsx`; links between pages keep it with `withRange`), charts are clickable (`BarChart`'s `onSelect`: a day's bar zooms to that day, which shows its hours), and `insights.tsx` draws the figures and the weekday and hour charts. Charts stay plain SVG (no chart library: the shop is on a metered hotspot).
- **Site data is admin-only** in both the worker and the UI (it is per-student browsing data). Hourly rows kept 30 days, then daily for a year.
- **Blocking (Phase 2):** admin-made blocklists, time-limited grants, and UI switches (`enforce`, `dns_hardening`) live in D1; every change bumps `net_settings.state_version` and pokes the agent (`POST /sync` over the link). The agent fetches `GET /agent/network/state`, applies it to its own `inet g3` table and `/var/lib/g3-edge/dnsmasq/g3-edge.conf` (built in `devices/edge-agent/src/modules/network/enforce.ts`), and acks. The UI shows "pending" until the applied version matches. Enforcement survives offline and reboots (last state saved in agent.db).
- **The link (no tunnel):** the worker reaches the box over one WebSocket the agent opens and keeps open (`devices/edge-agent/src/core/link.ts` → `wss://<number>-edge.<platform>/api/agent/connect` with the team's box key in `EDGE_AGENT_KEY`), held by the team's `AgentLink` Durable Object (`workers/edge/src/lib/agent-link.ts`, SQLite-backed, hibernating; named `team:<teamId>`, one per team). `agentFetch(env, teamId, path, init)` sends an HTTP request down it; the agent runs it on its own API (`createAgentApp` in `core/server.ts`) with the key added and streams the answer back. Frames (`src/lib/link-protocol.ts`, `@g3/worker-edge/link-protocol`) are a 4-byte header length + JSON header + body bytes, bodies in 256 KiB pieces (print jobs reach 50 MB; a WebSocket message can't). Heartbeat: the agent sends `ping` every 25 s, the Durable Object auto-answers `pong` without waking, and the agent reconnects (backoff to 60 s) after two missed answers or any close. Box not connected or too slow → `AgentError` 503. `/status/connection` checks it. Nothing on the box listens on the internet.
- **Single edge device, no HMAC, no Cloudflare Access, no SSH from the internet** (SSH on `wan0` is temporarily allowed by a `# TEMP` rule in `nftables.conf`). The agent never touches base netplan, nftables, or dnsmasq config; `nftables.conf` must not `flush ruleset` (it would delete `inet g3`). The agent's API (`POST /sync`, `/print/*`, `/lookup`, `/switch/*`, `/network/*`) requires the shared key; it's also served on 127.0.0.1:8700 for checks on the box, where `/health` needs none.
- **Printing:** replaces the old shoppi-print server. Shop worker `/print` (unchanged API; forces one-sided black and white) → `EDGE` service binding → edge worker `/print/*` → `agentFetch` (over the link) → agent `modules/print` → CUPS (`lp`/`lpadmin` to change things, a small IPP client in `ipp.ts` to read printers and jobs). **Nothing is stored**: no R2, no job table; CUPS on the box is the source of truth, and an unreachable box is an immediate 503. Anyone logged in can print; admins manage printers; members cancel only their own jobs (jobs are submitted with `lp -U <G3ID user id>`). Wire types live in `workers/edge/src/modules/print/types.ts`, exported as `@g3/worker-edge/print-types`. The agent needs to be in the `lpadmin` group.
- **Shop drive:** `devices/edge-agent/src/modules/drive` runs its own HTTP server on the box's LAN address, port 80 (`http://drive.local`, announced over mDNS by `g3-drive-mdns.service`; also `http://192.168.50.1`). It's a self-contained page plus `/api/files` and `/files/:name` (Range downloads). **No auth, by design**: anyone on the LAN can upload, download, and delete low-risk files. It's never reachable over the link, so file traffic never crosses the internet. Storage is a 10 GB loop-mounted image at `/srv/g3-drive` (`infra/edge/setup-drive.sh`); the agent refuses to write if it isn't mounted. The dashboard's Drive page only links there: an https page can't call a plain-http LAN address.
- **Power cuts:** the box is unplugged without warning, so nothing it needs may depend on a write from the last few seconds. Its root filesystem runs `data=ordered` with the default commit (Armbian ships `writeback` + `commit=120`, which left files empty after a power cut; `infra/edge/README.md`), `install-agent.sh` refuses empty files and `sync`s, and dnsmasq creates its own query-log folder on every start (`etc/systemd/system/dnsmasq.service.d/g3-edge.conf`), so DHCP and DNS never depend on `tmpfiles.d`.
- **Door sounds:** `devices/edge-agent/src/modules/switch` reads the Orange Pi 5's GPIO2_D4 (physical pin 22 / GPIO 92). The door-closed microswitch grounds the pulled-up input; the opening transition plays a WAV through `aplay` to the Orange Pi 5 analog headphone jack (`EDGE_SWITCH_AUDIO_DEVICE`, default `plughw:CARD=rockchipes8388,DEV=0`). Admin-only `/switch/*` worker routes and the Edge app's Door Sounds page manage, test, and delete WAV files stored on the box in `/srv/g3-sounds`; audio is not stored in Cloudflare.
- Local dev: `pnpm --filter @g3/edge-agent run dev:mock` runs the agent with fake counters against the local worker, and opens its link to it (run `pnpm --filter @g3/worker-edge box-key:set -- --local --key local-dev-agent-key` once (stores the mock agent's key, from `mock.env`, as the site team's box key)). The agent logs `[link] connected to the worker`; its `/health` shows `link`.

### Pit log downloader

- `devices/pit-log-downloader` (`@g3/pit-log-downloader`, its own version like the edge agent): runs on a pit computer (Linux, Windows or macOS) on plain Node 24 (`pnpm --filter @g3/pit-log-downloader start`, which builds the status page first). It does nothing until it's paired with its team's Pit (below), which gives it its team. Then, when the computer joins the robot's network (`10.TE.AM.x`, from the paired team's number), it copies AdvantageKit `.wpilog` match logs off the roboRIO over SFTP (node-ssh), names them by match and event, and uploads them to the team's Pit (below) whenever it's online. Its status page (`web/`, on `127.0.0.1:3000`) is React + Vite + Tailwind from `@g3/ui`'s parts, under `AppNavBar` with `team={false}` (no sign-in, no app list): it's a tool on the team's computer, not a team's app. Once paired it takes its team's Team Appearance (colors, names, logo online, the tab title): the page's `@g3/ui` loads `/team/ui` from the downloader itself (`VITE_G3ID_API_URL` = `/api/gearbox` in its `vite.config.ts`), whose `GET /api/gearbox/team/ui` asks Pit's `GET /downloader/team-ui` (with its key; Pit asks G3ID's `/team/ui` over its binding with `X-Team-Id`) at most once a minute, keeps the last copy in `DATA_DIR/appearance.json` for offline, and falls back to the team's defaults. Before pairing it's in the built-in colors; pairing and unpairing reload the page. The server (`src/`, Express) answers `/api/status` (its shape is `src/status.ts`, imported by the page) and `/api/download`, and serves the built page from `dist/web`; `watch` runs Vite inside it (`--watch-page`) instead. `--dev` (`start -- --dev`, `watch -- --dev`) pairs with the team's Pit through the dev gateway (`teamAppUrlVia` with the gateway's URL from `.dev-ports.json`: `http://1648-pit.gearbox.localhost:8796`). Moved in from the old Pit-Log-Downloader repository.
- **Match logs in Pit** (roadmap L.3, L.4): the downloader uploads each copied log it hasn't yet (`uploadLog` in `src/gearbox.ts`, one at a time while online, `status.uploaded` in `logs.json`) to Pit's `/downloader/logs` routes (`workers/pit/src/match-logs.ts`, `requireDownloader`): `POST` starts one (answers `exists` when Pit has the same event, name and size), `PUT /:id/parts/:n` sends 10 MiB parts (R2 multipart: Workers refuse request bodies over 100 MB), `POST /:id/complete` stores it. Files are in Shop's R2 bucket (`LOGS` binding, `g3-bucket`) under `pit/teams/<team>/logs/<event>/<name>.wpilog`, outside Shop's own `teams/<team>/`, which Shop deletes when it's switched off; rows in `match_logs` (migration `0014`, one per team, event and name). Pit's Logs page lists them by event (`plugins/logs/match-logs.tsx`, `GET /logs`), downloads (`GET /logs/:id/file`) for anyone signed in and deletes (`DELETE /logs/:id`, `DELETE /logs`) for admins only (`requireAdmin`; `canDelete` in `GET /logs`). Pit's delete hook deletes the files; its export leaves them out. There's no Google Drive any more.
- **Limits** (`MAX_SIZE`, `MAX_LOGS` in `match-logs.ts`): logs are gzipped (level 9) on the downloader and stored gzipped (`.wpilog.gz`; `size` is gzipped, `raw_size` the .wpilog's, `trimmed`, migration `0015`); one over 40 MiB gzipped isn't taken (`too_big`) and waits on the downloader until it's trimmed. A team keeps at most 20: its choice `matchLogsWhenFull` (Pit `settings`, manifest setting, `PUT /logs/settings`, mentors and admins, on the Logs page) is `skip-new` (default: `POST /downloader/logs` answers 409 `full`, and the downloader waits 5 minutes before trying again) or `delete-oldest` (completing an upload deletes the oldest beyond 20). A single log downloads with `Content-Encoding: gzip` (`encodeBody: "manual"`), so the browser saves a plain .wpilog. `GET /logs/export.zip` is every log as one zip of .wpilog files, built by `src/zip.ts` from the gzip files as they are (the deflate data between the gzip header and trailer, whose CRC-32 and size go in the zip's headers: no recompressing or hashing); the Logs page's Export and delete all then asks, once the download has finished, to delete the logs it held (`DELETE /logs { ids }`). The Logs page has a beta note at the top.
- **Trimming** (the downloader, `src/wpilog.ts`): `timeline` reads a .wpilog's bytes per second and the enabled and autonomous spans (AdvantageKit's `/DriverStation/Enabled` and `/Autonomous`), and suggests 15 s before the first enable to 15 s after the last disable; `trim` writes the part kept, every entry still started and its last value before the cut repeated at the start. The status page's Trim dialog (`web/src/trim-dialog.tsx`, `GET`/`POST /api/logs/:id/trim`) charts it with two sliders, a Suggested trim and the size it comes to gzipped; the file on the computer is never cut. Pit's Monitor shows a Logs section while the team has a paired downloader (the downloader's status, then the 3 newest logs), under the stream link's feed (shown only when the link is set); In the pit now is at the top of its left column. The Monitor asks Pit's `/health` every second (`plugins/pit-monitor/connection.tsx`): an Online dot with the last answer's time in its header, and after two failed checks in a row a full-screen Offline notice until it answers again, when it reloads at once; a failed refresh keeps each part as it last was.
- **Status in Pit**: the downloader tells Pit what it's doing every 10 s while online (`POST /downloader/status`: on the robot's network, whether the roboRIO answered, logs copying, the one uploading, how many wait), kept on its `log_downloaders` row (`status`, `status_at`, migration `0017`); `GET /downloaders` adds `status` and `online` (said so in the last 45 s). Pit's Logs page (a Log downloader card, asked again every 10 s) and the Monitor's Logs section show one (`shared/downloader-status.tsx`: online first, then the one heard from last). On the downloader, the robot is Connected as soon as the computer is on its network (`10.TE.AM.x`); listing and copying its logs runs beside the 3-second loop (never holding it, or the page), again every 30 s while connected; a copy goes to `<log>.part` and is renamed when whole, and is stopped (the connection closed, tried again at the next check) when the robot's network goes, when it moves no bytes for 30 s, or when SSH keepalives go unanswered (about 15 s); and the Robot tile says when the roboRIO isn't answering. Once a minute it asks Pit which logs it has (`GET /downloader/logs`), so its "In Gearbox" tags follow Pit: one deleted there says Deleted from Gearbox and isn't uploaded again.
- **Pairing with Pit** (roadmap L.2): Pit's Logs page (`apps/pit/src/plugins/logs/`) shows a team with no downloader the setup steps for Windows, macOS and Linux (`setup-steps.tsx`, with the team's `TEAM_NUMBER` and, off the usual address, `PIT_URL` filled in) and lets a mentor or admin get a 6-digit code (`POST /downloaders/codes`, `requireMentor`; one per team, 10 minutes, once, dead after 5 wrong tries). Until it's paired the downloader's status page is only a pairing form (team number, code, the computer's name). It sends them to its own `/api/gearbox/pair`, which posts the code to `POST /downloaders/pair` on that team's Pit address (no session: the team is the address, `requestTeamId`), and gets back a key (`pld_…`) kept with the team number and Pit address in `DATA_DIR/gearbox.json` (mode 600; a saved pairing for another Pit than the one now set, by `PIT_URL` or `--dev`, is ignored). Pit keeps only its SHA-256 (`log_downloaders`, `log_downloader_codes`, migration `0013`; `workers/pit/src/downloaders.ts`), lists them for anyone signed in (`GET /downloaders`), and mentors remove one (`DELETE /downloaders/:id`). Routes for the downloader go behind `requireDownloader` (`Authorization: Bearer <key>`, on its own team's address; sets `downloaderId`): `GET`/`DELETE /downloader/me`. The downloader checks its key every minute while online and unpairs itself if Pit removed it; unpaired (by itself, its page or Pit), it stops until it's paired again with a new code. Pit's setup steps add `-- --dev` to the start command on a local Pit and a `PIT_URL` line off the usual address. Its local API refuses a Host that isn't loopback (DNS rebinding) unless `HOST` opens it, and any change that isn't JSON (another site's form). Pairing and codes are in `DEMO_BLOCKED`, and the team's log records pairing and removal.
- Settings are optional, in its gitignored `config.env` (`config.env.example`, read by `src/config.ts`), never in code: data folder, port, host, and `PIT_URL` for a Pit off the team's usual address (staging). There's no `TEAM_NUMBER`: the team comes from pairing. Its data (`logs.json`, `logs/<event>/`) is in `DATA_DIR` (`data/`, gitignored), and each log's local path is worked out from it, never stored. Paths on the roboRIO always use `/`; paths on the computer always go through `node:path`.
- `ssh2`'s native add-ons are off (`allowBuilds` in `pnpm-workspace.yaml`), so it installs without a compiler. `pnpm --filter @g3/pit-log-downloader smoke` starts it and checks its status page; `.github/workflows/pit-log-downloader.yml` runs that on all three systems.

### AdvantageScope in Pit

Keep it that small; upgrading is moving the submodule to the next stable tag and fixing the patch.

To stay in a Worker's memory the zip is held once, as the request's body (`multipart.ts`, not `formData()`), every file is unzipped and checked once before anything is stored, then each is streamed into R2 (`FixedLengthStream`), never held whole; one with the same name replaces it) and `DELETE /assets/:name`; `GET /asset-list` for the Logs page; `GET /sign-in` (a signed-out visitor goes to the team's ID sign-in and back, only to a `/scope/` page). - **Pit's AdvantageScope page** (`/logs/advantagescope?log=<file>`, `plugins/logs/advantagescope-page.tsx`; under Logs, which stays the bar's current page, with no bar entry of its own): the team's match logs to choose from, and `/scope/` in a frame filling the rest of the window; choosing a log loads it again with `?log=`. ### G3 Orders (parts ordering)

- **Team-scoped** (roadmap Phase 3): 16 of its 17 tables carry `team_id` (migration `0018`), and every query goes through `inTeam`/`withTeam` (in the tenancy lint). Keys are unique within a team (budget category names, `vendors` by team + key, `app_settings` by team + key, catalog category names, FRCDesign `source_id`s, order-sheet `import_key`s). `lookup_cache` is shared: vendors' public product pages. `test/isolation.test.ts` is its two-team test; `test/teams.test.ts` covers settings, the starter catalog and Slack per team.
- **Each team's settings** (`src/lib/settings.ts`, rows in `app_settings`): currency and fiscal-year start month (G3's rows: USD, July; a new team gets the same defaults), the default sales tax rate (`salesTaxPercent`, 0–100: the tax a new order on the Carts page starts with, as a percent of its items, except at tax-exempt vendors; G3's row is 8.9 from migration `0020_sales_tax.sql`, a new team's is 0), the naming template and whether receiving needs an Inventory place. Mentors edit them on its Admin page (`/admin`; `PUT /settings`); `GET /me` returns currency, start month and the tax rate for every page (the app's `formatCents` uses the team's currency, set from `/me`). There's no team time zone: dates are the viewer's local time. The app sends the browser's zone with every call (`X-Time-Zone`, `localTimeHeaders` in `apps/orders/src/shared/api.ts`), and the worker uses it (`localTimeZone(c)`, `src/lib/local-time.ts`; UTC without one) where it turns moments into dates: fiscal-year boundaries, export dates, imported sheet dates, Share-A-Cart cart titles. Calendar days (need-by, expiries) are stored as 16:00 UTC that day and shown in UTC (`formatDay`), so they're the same day in any zone.
- **The parts catalog is per team.** The FRCDesign parts are kept once under the team id `starter` (migration `0018` made it from G3's catalog, without prices, counts or editors' names); `ensureCatalog` / the `catalogReady` middleware (`src/lib/starter.ts`) copies it to a team in one guarded batch the first time it needs its catalog (`/me`, `/catalog*`, `/suggest`, creating or editing a request). After that the copy is the team's: edits, prices and new parts stay with it. A script-generated catalog fix (`scripts/catalog-*.py`) must update every team's copy and the starter, and only parts still as the starter had them.
- Any member requests one line (vendor link, quantity, budget category, reason). **Only G3ID mentors and site admins** (`is_mentor` or `is_admin`, never kiosk sessions) approve/deny, mark ordered (with actual cost) and manage budget categories. Statuses: requested → approved/denied → ordered → received, or canceled (requester or mentor, before ordering; the stored status value is spelled `cancelled`). **Anyone signed in** (kiosk sessions too) marks an ordered request received: packages are opened by whoever is in the shop.
- `workers/orders` (Hono, Drizzle, D1 `ORDERS_DB`): `/requests` (list, detail with history, create, edit while requested, or by a mentor while approved and not yet ordered: it stays approved, with a `reapproved` event saying what changed, `POST /requests/:id/:action`), `/categories` (with spent/committed/pending totals), `/lookup?url=` (7-day cache in `lookup_cache`). Status changes are conditional updates on the expected status, and every change is logged in `request_events`.
- Approval sends the requester a DM on their team's own chat, Slack or Discord (`sendMemberDM` with their G3ID user id, through G3ID; nothing is sent if the team has no chat or they haven't linked it), with a link to the team's own Orders address (`src/lib/urls.ts`, through the dev gateway in dev via `LOCAL_GATEWAY_URL`). `requester_slack_id` is no longer written.
- Part lookup runs **on the edge box** so vendors see the shop connection, not a Workers IP: orders `/lookup` → `EDGE` service binding → edge worker `/lookup` → `agentFetch` → agent `modules/lookup/part-lookup.ts` (Shopify, including the linked products behind Itoris "Dynamic Product Options" dropdowns on placeholder products like WCP's Tube Plugs, BigCommerce, JSON-LD, Amazon, DigiKey API via `EDGE_DIGIKEY_*` in agent.env). The requester's browser headers (User-Agent, Accept-Language, Sec-CH-UA; never cookies) are forwarded for fetches that must look like a browser (Amazon), except that a phone's are swapped for a desktop browser's (Amazon's mobile page lacks the product details; the name also falls back to the mobile title and the page title, and only a real CAPTCHA page is reported as a bot check); Shopify gets an honest user agent because a fake Chrome one gets 429s. McMaster's API is B2B-only, so McMaster links only yield the part number (and name when prerendered). Wire types: `@g3/worker-edge/lookup-types`. Box offline → lookup fails with 503 (no fallback); requesters can fill details by hand. Orders and Shop call Edge as the member, for their team (`forwardIdentity`), so each team's lookups and prints go to its own box; a team without a connected box gets 503 "isn't connected". The agent meters lookup traffic (compressed wire bytes + headers, via `fetch` with `decompress: false`) into the network usage buckets under the pseudo-client `_lookup`; the Network overview shows it as "Part lookups". Usage keys starting with `_` are never LAN clients. Local dev: run the mock agent (`pnpm --filter @g3/edge-agent run dev:mock`) after `pnpm --filter @g3/worker-edge box-key:set -- --local --key local-dev-agent-key` once (stores the mock agent's key, from `mock.env`, as the site team's box key); without it the worker refuses the agent's link and lookups fail with 503 "isn't connected".
- `apps/orders`: plugin-based UI (from `apps/edge`): Requests (`plugins/requests/requests-page.tsx`: a sheet-like table, one grid with subgrid rows so prices and dates are never cut off; sections Pending → Approved → Ordered → Received, then denied/canceled; your own first, then oldest; filters, "only mine" and the search live in the address; `GET /requests` adds `orderedAt` (the vendor order) and `receivedAt` (latest receipt)), New Request (the "why" is optional everywhere; see below), Approvals (mentors; "Replace item" swaps in another link through the same lookup as New Request (`plugins/requests/draft.tsx`), keeping quantity, category, priority, need-by and reason; logged as a `replaced` event with the old item), Carts (`/ordering`, mentors: approved lines grouped by vendor, each card also shown on an approved request's page (`VendorCart`); `POST /requests/order-batch` marks many ordered and splits an optional real order total across them by estimate), Budget.
- Money: only placed vendor orders count against budgets (final qty × price, or an imported line's exact `line_total_cents`, plus the order's fee rows in `order_charges`: Shipping/Tax/Tariff per category; new orders split fees by item cost). `GET /orders/export.csv` writes the team's order-sheet columns; `POST /orders/import` (Budget page, `?dryRun=1` previews) reads the same format back, matching Budget Cat codes to categories and skipping rows imported before (`import_key`).
- Fiscal years start on the 1st of the team's start month at midnight in the viewer's local time (`src/lib/fiscal.ts`, which takes a `FiscalCalendar`: the team's start month and the request's zone; named by starting year: 2026 = "2026–27", or "2026" for a January start). Budgets are per category per year (`category_budgets`); spending counts in the year an order was placed. The Budget page has a year picker and the team's summary table; exports are per year.
- Vendors are matched by lowercased name (`vendors` table holds profiles: tax exemption, shipping thresholds, minimum, lead/shipping days, cutoff, payment, credits in `vendor_credits`). Students only get lead/shipping days (for place-by dates). The Carts page shows profile nudges and marks carts with Blocking or late items "Place today". Requests have `priority` (blocking/high/normal/nice, anyone can set) and `need_by`; place-by = need-by − lead − shipping days.
- Fast entry: New Request takes several links at once; `POST /suggest` returns the templated name (`src/lib/naming.ts`, template in `app_settings`, default `{vendor} {sku} – {title}`), a budget-category guess (last purchase of the same product → vendor default → `category_rules` keywords, whole word) and "bought before" history (same Amazon ASIN / host+path, or same SKU at the vendor). For a part new to the catalog it also guesses the catalog category from light built-in keywords (`src/lib/category-guess.ts`, only categories that exist). Guessed values show an amber "check it's right" hint until the requester changes them. Mentors edit the template and keyword rules on the Admin page.
- Deliveries page (`/receiving`): `GET /orders/receiving` (orders with items on the way + received in the last 14 days), `POST /orders/receive` (anyone signed in), `PATCH /orders/:id/tracking` (mentors). Tracking links guess the carrier from the number.
- One-click carts: Shopify cart permalinks (`apps/orders/src/shared/cart.ts`: `/cart/<variant>:<qty>,…`, variant from `store_variant_id` saved at request time or `?variant=` in the link) and, for Amazon only, Share-A-Cart (`workers/orders/src/lib/share-a-cart.ts`: each team's account connected once on the Admin page over OAuth, kept in the team's settings encrypted with the worker's `SECRETS_KEY` (older plain rows are read and encrypted on first read), calling back on the team's own address; carts saved through their MCP `sac_save_cart` tool). ### G3 Shop: batches and files

- A process is `regular`, a **File Producer** (makes a file: CAM, slicing) or a **File Consumer** (uses it: a router, a printer). A part's processes have both kinds or neither, and each File Consumer step comes after a File Producer one (`fileStepError` in `workers/shop/src/lib/process-rules.ts`, shared with the app).
- **A batch** (`staging_batches`, rules in `workers/shop/src/lib/batches.ts`, routes in `routes/staging-batches.ts`) is instances that share one file and move as one unit: through the File Producer process it was made at (`producer_status`), then the File Consumer process its parts go to next (`consumer_process_id`, `consumer_status`). **It is the only thing that links an instance to a file** (migration `0019_batches.sql` turned files assigned straight to instances into batches and dropped `part_instance_files`). A part can also go through a File Producer process on its own, with no batch and no file.
- An instance is in a batch while its step at the batch's File Producer process carries the batch's id (`part_instance_processes.batch_id`). It joins while it is at that process, in no other batch and headed for the same File Consumer process as the batch's others (`stageInto`), and takes on the batch's status there; taken out (`unstageFrom`), it goes back to To Do. Once the batch has finished that process nothing joins or leaves that way: the whole batch is sent back (`sendBatchBack`), or one instance is (`sendInstanceBack`: back to To Do at the File Producer process, with a row in `staging_batch_removals` so the batch still shows it was there).
- **A step a batch moves can't be moved on its own.** The single-part routes (`part-instance-processes.ts`: `/doing`, `/done`, `PATCH`, `/bulk`) refuse or skip a batch's File Producer and File Consumer steps (`governingBatch`, `governedInstances`). A new route that changes a step's status must do the same.
- A batch's name is the one it was given (`name`), else its part and count when it holds one part ("Side Plate × 4"), else "Batch" and its number, counted up within the team (`batchLabel`; the worker sends it as `label`). A batch can be completed without a file. It is deleted only while at its File Producer process. `duplicatePlan` / `duplicateBatch` copy one: the same file and as many of each part as it was made with, from those waiting at the process in no batch.
- **A file is obsolete** once any instance it was made for is (in one of its batches, or sent back out of one), and can't go on another batch (`obsoleteFileIds`). Deleting obsolete instances (Admin) sets `files.obsoleted_at` first, so it stays obsolete.
- In the app, shop data (parts, processes, batches) is one copy shared by the bar, the page and anything opened over it (`shared/use-shop-data.ts`; `refreshShopData()` reloads it for all of them). `shared/batches.ts` reads batches for the pages (which batch moves a part's step, a file's and a drawing's status). A batch's **detail view** is `BatchSheet` (`plugins/batches/batch-sheet.tsx`), a full-screen view like a part's, opened over any page by `?batch=<id>` in the address (`BatchLink`); a batch has no shop view, so kiosks use it too. The Shop Floor shows a batch as one row at its two processes (`producer-process-view.tsx`, `consumer-process-view.tsx`), a part's Files panel lists its batches (`part-files-panel.tsx`), and the Files page groups files (Not Started, In Progress, Complete, Unused, Obsolete) by their batches and drawings by their parts' progress. Names are links, and part numbers stay plain text: a batch's name opens its view, a file's downloads it, a part's opens its page, and a part's name with an instance number opens that instance's details (`plugins/batches/batch-ui.tsx`). Buttons follow the Shop Floor's own: Start, the green Mark as complete (`CompleteButton`), Stage and Unstage, and Send back as a secondary button that asks in a `Dialog`.

### G3 Skill Tree (skills each student has learned)

- Skills are grouped into trees (Safety, Manufacturing, ...) and categories. A skill opens when the skills it comes after (same category) are complete, a category when the categories before it (same tree) are, and a tree can wait on another tree (`requires_tree_id`; every tree in the default set waits on Safety). An empty category or tree counts as complete. That logic is in the page (`apps/skill-tree/src/shared/progress.ts`); the worker stores what mentors set and doesn't enforce locks, so bulk sign-off can skip them.
- **The trees are a team's content, not part of the app.** A team's trees are one *tree set* (a `tree_sets` row; `workers/skill-tree/src/lib/tree-set.ts`), saved to and loaded from a JSON file (`"format": "gearbox-skill-trees"`, `"version": 1`: trees → categories → skills, each named by a `key`, with `requires` lists of keys; described in `apps/skill-tree/README.md`). The set every team starts with is `workers/skill-tree/content/default-trees.json`. It is loaded the first time anyone opens the app (`currentTreeSet`, the stand-in for the seed hook of roadmap step 4.3) through the same code as any team's file. **No migration holds trees and no code names one**: the app must work the same on any set.
- Loading a file (`applyTreeSet`, one D1 batch, all or nothing) makes the trees match it **by key**: what's still in the file is updated in place (a skill keeps everyone's progress even if the file moves it to another category), what's new is added, and the rest is deleted with the progress on it. `parseTreeSet` checks a file and reports problems in words a mentor can act on; `POST /trees/import/preview` says what a load would add, remove and delete before anything changes. Keys are unique in the set (trees, skills) or in the tree (categories); things made in the editor get a key from their name (`keyFrom`).
- **Students are the team's active members that aren't mentors** (`lib/roster.ts`, from `@g3/auth`'s `activeMembers`, which reads G3ID's member list with roles). Skill Tree keeps no list of people, only `skill_progress` by G3ID user id, so everyone shows up without opening the app and nobody is added by hand. Admins who aren't mentors are students.
- **Anyone signed in** (kiosk PIN sessions too) reads the trees and everyone's progress. **Only G3ID mentors and site admins** (`requireMentor`, never kiosk sessions) sign skills off, edit trees and save or load tree sets. There is no app-level mentor list.
- `workers/skill-tree` (Hono, Drizzle, D1 `SKILL_DB`): `/trees` (the set's name and all its trees with categories, skills and what each requires; mentors `POST`, `PATCH /:id`, `DELETE /:id`, `PUT /order`, `POST /:id/categories`, `GET /export`, `GET /default`, `POST /import/preview`, `POST /import`), `/categories/:id` (`PATCH`, `DELETE`, `POST /:id/skills`), `/skills/:id` (`PATCH`, `DELETE`), `/students` (every student and each started skill's status), `/students/:userId` (one student's progress with who signed each skill off), `PUT /students/:userId/skills/:skillId`, `GET /students/by-pin/:pin` (mentors; asks G3ID whose kiosk PIN it is), `POST /progress` (one status for up to 100 students × 100 skills, 2,000 marks at most). Sign-offs are refused for anyone who isn't a student. Prerequisites must stay inside the category (skills) or tree (categories) and can't loop: a loop is refused with a 400. Every query is kept to the team's tree set.
- Tables (all one team's data, rooted at `tree_sets`, the one table with a team: `team_id`, one set per team, migration `0004`): `tree_sets` (team, name, who last loaded it), `trees`, `tree_categories`, `category_prereqs`, `skills`, `skill_prereqs`, `skill_progress` (G3ID user id × skill, status `in-progress`/`complete`, who set it and when; no row = not started). Every query is kept to the team's set: `currentTreeSet(db, c.get("teamId"))`, then the set's id. Deleting a tree, category or skill deletes the progress on it. Migration `0003` dropped the old tables: everyone's earlier progress was cleared on purpose. `test/isolation.test.ts` is its two-team isolation test.
- `apps/skill-tree`: plugin-based UI (from `apps/orders`): Overview, Skill Trees (`/trees/:treeId?student=&category=&skill=`; `plugins/trees/layout.ts` places the boxes and routes the lines), Sign Off and Edit Trees (mentors; its Tree set card saves the set to a file and loads one, showing the preview first). Trees and progress are loaded once and shared (`shared/skill-data.tsx`); progress refreshes on focus and every minute. Each D1 statement stays under 100 bound parameters (`chunks` in `src/lib/input.ts`).

### G3 Inventory (what the team owns and where it is)

- An **entry** (`items`) is one kind of part: a name, the team's own **fields** (`field_values` JSON by field id) and its **vendor listings** (`item_listings`: one vendor's SKU each; equivalent parts from different vendors are several listings on one entry). Stock is counted per place (`stock`): a **location** in storage, or a location plus the **robot** and **subsystem** it's in use on. One row per entry per place; quantity can't go below zero (a CHECK, which fails the whole batch).
- **The arrangement is a team's content, not part of the app.** Fields (`fields`: text, paragraph, number, choice, checkbox, link, date), the tree of locations (`locations`, at most 4 levels: `MAX_DEPTH`), `robots` and `subsystems` are rows a team makes on its Admin page or loads from a *setup file* (`"format": "gearbox-inventory-setup"`, `workers/inventory/src/lib/setup.ts`; described in `apps/inventory/README.md`). Loading only adds what's missing, matched by name; nothing is changed or removed. A database starts empty; the starter that comes with the app is `workers/inventory/content/starter-setup.json`. **No migration holds any of it and no code names a location, robot or field.**
- **Anyone signed in** (kiosk PIN sessions too) reads everything, adds and edits entries, counts, moves, checks out and in, adds or removes listings, gives a location its title and moves everything in a location. **Mentors and admins** (`requireMentor`) delete, merge and split. **G3ID admins** (`requireAdmin`) use the Admin page.
- `workers/inventory` (Hono, Drizzle, D1 `INVENTORY_DB`): `/inventory` (everything the table shows), `/options` (locations, robots, subsystems), `/items` (`POST`, `GET|PATCH|DELETE /:id`, `POST /:id/stock`, `POST /:id/listings`, `DELETE /:id/listings/:listingId`, `POST /:id/merge`, `POST /:id/split`), `/stock/:id` (`PATCH` quantity = a count, locationId = move; `POST /:id/check-out`, `POST /:id/check-in`), admin `/fields`, `/locations`, `/robots`, `/subsystems` (each with `PUT /order`), `/setup` (`export`, `starter`, `preview`, `import`), and `/intake`.
- **Team-scoped** (roadmap Phase 3): all nine tables carry `team_id` (migration `0003`), and every query goes through `inTeam`/`withTeam`, including the stock helpers' subqueries (stock aliases `s`/`t`, which the tenancy lint also checks). The routes take the team from `c.get("teamId")`; `loadItems`, `loadFields`, `loadLocations`, `loadNames` and the stock helpers take it as an argument. Guarded inserts (`INSERT … SELECT … WHERE`) go through `insertWhere` (`src/lib/guarded.ts`). `test/stock-guards.test.ts` covers the guards directly; `test/isolation.test.ts` is its two-team test. Orders sends deliveries with the member's team (`forwardIdentity`).
- Stock changes are one D1 batch each (`src/lib/stock.ts`): take from the row, add at the new place, log the history line, tidy up. Later statements only act if the row taken from still exists, so two people moving the same parts can't both win. An emptied in-use row is deleted, and so is an emptied storage row when the entry has another storage row; an entry's only storage row stays at zero (so an entry with everything on a robot remembers where it's kept) until stock lands in storage somewhere else. The table shows a row per place with parts, or that zero row when there are none. The Check in pop-up is preset to the entry's first storage row (`storageHome` in `apps/inventory/src/shared/stock-dialogs.tsx`), so parts join it; Check out is preset to stay where the parts are.
- Every change to an entry is a line in `item_events` (its History): created, edited, added, counted, moved, checked_out, checked_in, received, linked, unlinked, merged, split. `ref` links a line to an Orders request (`orders:request:<id>`) or another entry (`item:<id>`).
- **Merge** moves the other entry's stock (adding quantities in the same place), listings and history into this one and deletes it. **Split** makes one listing its own entry, with the quantities the mentor says are its.
- **Orders' catalog:** a listing can carry `catalog_item_id` (a part is on one entry at most). Inventory's prices are per part: a catalog part that's a pack of 4 for $17.50 shows as $4.38 each (`partPriceCents`). The page reads the catalog through `apiPath("orders")` (`apps/inventory/src/shared/catalog.ts`) to show the product page, what was last paid and a Request button; a typed-in listing with the same vendor and SKU, or link, is shown the same way. The worker has no binding to Orders, and a listing keeps its own copy of vendor, SKU, link and price, so Inventory works without it.
- **Location titles and the Locations page:** a location has a `title` (migration `0002_location_titles.sql`): a few words on what's kept there, which pages call its description. Wherever a location is named it reads "name - title" (`labelOf` in `workers/inventory/src/lib/locations.ts` and `apps/inventory/src/shared/places.ts`; Orders' receive pop-up does the same), so history lines say "Dungeon › A1 - Misc. Electronics". The Locations page (`/locations`, `apps/inventory/src/plugins/locations/`) is the table turned round: nested panels that open, each location with what's kept directly in it, a Move button per entry (the whole row) and, under the entries, "Move all" for everything in the location. A panel's first line is its name, an "Add description" text button and, always at the right, its count; a description shows on its own line under the name, with Edit (the box opens there: Enter or clicking away saves, Escape or Cancel doesn't). `routes/location-contents.ts`: `PUT /locations/:id/title` and `POST /locations/:id/move-contents` (`moveLocationContents` in `lib/stock.ts`: one batch; rows merge with the entry's row already at the new place; the tree itself never changes). Both are for anyone signed in, unlike the tree's own editing on the Admin page.
- **Ordering locations:** on the Admin page, admins drag a location by its handle to put it in order among the ones in the same place (`apps/inventory/src/plugins/settings/locations-card.tsx`, with `@dnd-kit`: one sortable list per place, drops limited to the locations beside the one dragged, and arrow keys that step to the next one beside it). It saves through `PUT /locations/order` with that place's ids in their new order; other places keep theirs. Moving a location into another place is still Edit's job. Use `@dnd-kit` for any other drag-to-reorder list.
- **Received orders:** Orders posts `/intake` (wire types: `@g3/worker-inventory/intake-types`) with the receiving person's session. A delivery finds its entry by listing (catalog id, else vendor + SKU, else link) or becomes a new entry, and is added once per `sourceKey` (`intake_receipts`). Each delivery can name its own `locationId`; every place is checked before anything is added. `POST /intake/places` answers where parts that are about to arrive are already kept (the entry's storage row), changing nothing.
- `apps/inventory`: plugin-based UI (from `apps/skill-tree`): Inventory (`/inventory`: the table; type a quantity to record a count, click a location to move, Check out / Check in pop-ups in `shared/stock-dialogs.tsx`; below 768px each row is two lines instead, like Orders' Requests table: the entry and its Check out / Check in button, then location, quantity and status, without the team's own columns (`NarrowRows` in `plugins/table/table-page.tsx`)), Add an entry (`/new`), Locations (`/locations`, above), an entry's page (`/items/:id`: details, where it is, vendor listings, history, merge and delete for mentors), Admin (`/admin`, admins). Everything is loaded once and shared (`shared/inventory-data.tsx`), refreshed on focus and every minute.

### G3 Schedule (who does what at each event, 15 minutes at a time)

- Not released yet. `apps/schedule` is a plugin-based UI (from `apps/inventory`; pages in `apps/schedule/README.md`: Schedules, a schedule's My schedule and Everyone grid, where editors drag to assign roles, its Settings page, Roles and Admin); `workers/schedule` (Hono, Drizzle, D1 `SCHEDULE_DB`) has the API below.
- **What it holds** (migration `0002`, `src/db/schema.ts`): a team's event schedules. A schedule (`schedules`: name, the event's time zone, `notify_minutes` before a role change for a Slack DM (5 by default; null for none), and `published_at`: students and Slack see it only once published) has days (`schedule_days`: the hours the event runs, the grid's edges), labeled periods that don't overlap (`schedule_periods`: Load in, Lunch, Practice Matches), and attendees (`schedule_attendees`: only the members going are in its grid). `assignments` is one row per attendee per 15-minute block with its role; no row is nothing assigned. `roles` are the team's own (Drive Team, Scouting, Pit, Break, Lunch), kept from event to event, archived rather than deleted; each has a `type`, `scouting`, `pit` or `other` (the default; migration `0004`). `notifications_sent` keeps the cron from DMing twice.
- **Times are wall-clock slots** (`src/lib/slots.ts`): a local date (`2027-03-12`) and a slot of that day, slot n being n × 15 minutes after midnight; a range ends before its last slot, so Lunch 12:00–1:15 is 48–53. Only "now" and Slack need the time zone (`slotAt`).
- **The database keeps the rules a route might forget:** blocks only for attendees (composite foreign key, cascading when one is removed), only on the schedule's days (cascading with the day), on the grid (CHECKs), once per person per block (primary key), and a role still assigned can't be deleted (`test/constraints.test.ts`). A period not overlapping another and blocks within a day's hours are checked in code.
- **Who edits** (`src/lib/editors.ts`, `canEdit`, `requireEditor`; `/me` returns `canEdit`): ID's mentors and admins, and the members they trust in this app (`schedule_editors`, chosen on Schedule's Admin page). Never a kiosk session. Everyone signed in reads published schedules.
- **API** (`src/routes/`): `/schedules` (list: published, plus drafts for editors; `GET /:id` the whole schedule: days, periods, attendees with names from G3ID, every assignment as ranges `{ userId, day, start, end, roleId }` and the team's roles; students get the same, and the pages show it as the whole grid or their own; editors `POST`, `PATCH /:id` (name, time zone, `notifyMinutes`, `published`), `DELETE /:id`, `PUT|DELETE /:id/days/:day` (changing hours clears blocks outside them, and is refused while a period is outside), `POST /:id/periods`, `PATCH|DELETE /:id/periods/:periodId`, `POST /:id/attendees { userIds }` (active members only), `DELETE /:id/attendees/:userId`, `PUT /:id/assignments { changes: [{ userIds, day, start, end, roleId | null }] }`: runs of blocks given a role or cleared, in one batch, later changes winning). `/roles` (everyone reads; editors `POST`, `PATCH /:roleId` (name, `type`, color: a preset key from `ROLE_COLORS` (no red) or a custom `#rrggbb`, `archived`), `PUT /order`, `DELETE /:roleId` only while unassigned). `/members` (editors: active members, to pick attendees). `GET /now?type=scouting|pit|other` (anyone signed in, kiosks too): who has a role of that type at this moment on the team's published schedules, with the role and when it ends (`src/lib/now.ts`); Pit's "In the pit now" reads it. `/editors` (mentors and admins: `GET`, `PUT|DELETE /:userId`).

### Versions and releases

- **App versions**: SemVer, one per app, shared by its page and its worker (Changesets `fixed` groups in `.changeset/config.json`; the edge agent has its own). The worker's `package.json` is the source: `/health` returns it (`import packageJson from "../package.json"`), and apps get it through `siteConfig()` as `appVersion` / `versionLabel()` from `@g3/site-config/versions` (shown in the navbar's tooltip and drawer). Never hard-code a version.
- **Platform version**: CalVer `YEAR.MONTH.N` in the root `package.json`; each release and the app versions in it are listed in `RELEASES.md`.
- **Branches**: work merges into `staging`, which deploys to **staging**; `public` is the released branch, deployed to **production** once the release workflow has committed the release. Both go through `.github/workflows/deploy.yml` (called by `staging.yml` and `release.yml`): migrations, then every app's worker, then the gateway. Cloudflare's Git integration (Workers Builds) isn't used. **For now** the repository variable `PRODUCTION_BRANCH` can be `staging`: then every push to `staging` also deploys production (after staging's deploy; `staging.yml`), and the release workflow doesn't; unset, production deploys only from releases. The repository variable `STAGING_BRANCH` likewise moves staging to another branch (a feature to try there; unset, `staging`), and running `staging.yml` by hand deploys the branch it's run on (`docs/deploy.md`, "Trying a branch on staging").
- **Staging** (`docs/deploy.md`, "Staging"): production's addresses with `-dev` on the first part, on g3robotics.com (`1648-orders-dev.g3robotics.com`, the platform at `dev.g3robotics.com`; `site.staging`). A staging build (`GEARBOX_STAGING=1` for pages, `define` `__G3_STAGING__` for workers) sets `isStaging` in `@g3/site-config`, and every address helper goes through `platformHost`/`platformLabel`, so **never build a platform address by hand** (`${label}.${site.platformDomain}`). Pages get a "Staging" banner from the `siteConfig()` Vite plugin. Each worker's `[env.staging]` is written by `pnpm configure` from its `[env.production]` with ids from `infra/staging/resources.json` (`pnpm staging:create` makes them): edit production's, never the generated part. Staging has its own Slack app, installed in G3's workspace, with its ids in `infra/staging/resources.json` (`slack`; `docs/deploy.md`, "Slack on staging"). `pnpm staging:copy-team` copies G3's data (only the site team's, for the privacy draft) from production into staging, leaving out sessions, codes, kiosks, encrypted settings and R2 (`scripts/staging-copy-team.ts`; Wrangler is run through `scripts/lib/wrangler.ts`, which avoids its npm check).
- **Every PR into `staging` that changes an app adds a changeset** (`pnpm changeset`: pick the app, patch/minor/major, a summary for users; `--empty` when nothing should be released). CI fails a PR without one. Shared packages (`packages/*`) are ignored by Changesets; record their changes against the affected apps.
- **Agents: write the changeset file yourself** (`pnpm changeset` is interactive). When a commit changes an app, add `.changeset/<short-name>.md` in the same commit:
  ```md
  ---
  "@g3/worker-orders": minor
  ---

  One line for the app's users: what changed for them.
  ```
  List each changed app once, by its worker package (`@g3/worker-<app>`, including `@g3/worker-portal`; the edge agent is `@g3/edge-agent`), with the bump from `.changeset/README.md`: **patch** for fixes and small tweaks, **minor** for new features that break nothing, **major** when users or deployers must act (a migration to run first, a removed page, a changed API). For changes that release nothing (docs, CI, tooling only), use an empty header (`---` then `---`). Say which bump you chose and why when you report the commit, so a person can check it; `pnpm release:preview` shows the resulting versions.
- **Releasing**: `.github/workflows/release-pr.yml` keeps one `staging` → `public` PR open, titled with the next release (`pnpm release:preview`, which runs the release in a throwaway worktree). Merging it (merge commit only) runs `.github/workflows/release.yml` on `public`: applies the changesets (`pnpm release:version`: versions, CHANGELOG.md files, platform CalVer, RELEASES.md), commits "Release <platform>", tags `v<platform>` and each app's version (`pnpm release:tag`), and merges `public` back into `staging`. It pushes with the `RELEASE_DEPLOY_KEY` deploy key, which is on both rulesets' bypass lists. Its push of the release commit starts the workflow again, which finds nothing left to release and deploys production (`deploy.yml`); only such a run deploys, so production is always a released commit.

### Hosting: one worker per app, one gateway

- Each app is one worker: in production it serves the built app (`[env.production.assets]` → `apps/<app>/dist`, single-page-app fallback) and its Hono API at `/api` on the app's own address. Only `/api/*` runs worker code (`run_worker_first`); each worker's default export is wrapped in `withApiPrefix()` (`@g3/site-config/worker`), which drops `/api` so routes stay written as `/requests`, like in dev where Vite's proxy drops it. Apps call `"/api"` (same origin) in production and dev; a page calls another app's API at `apiPath("<app>")` (`/api/~<app>` on its own address: the gateway sends it to that app for the same team, and in dev the `siteConfig()` Vite plugin proxies it to the app's local worker). `apiUrl("<app>")` (`https://<app>.<domain>/api`) is only for addresses outside services call, like webhooks.
- **Workers call each other at `/api` too** (`http://g3id/api/auth/me`, `http://edge/api/lookup`): in production, anything outside `/api/*` would get the app's page.
- `workers/gateway` owns the platform's domain (`<platform>/*`, `*.<platform>/*`) and forwards each hostname to its app's worker through a service binding. It also still owns `*.<domain>/*`, G3's own domain, only to answer G3's retired addresses (`<app>.<domain>`, `api.<app>.<domain>`, `id.<domain>`, `admin.<domain>`) with `410 Gone` and the new address (`RETIRED_HOSTS`), and passes other hostnames (`www`, the edge tunnel) through. Portal has a tiny worker (`workers/portal`) just to serve its page.
- **Teams in the gateway** (`workers/gateway/src/index.ts`): every team, G3 included, is at `<number>-<app>.<platform>` (its home at `<number>.<platform>`); `<number>-<app>.<domain>` is that team's app and `<number>.<domain>` its home (Portal), 404 unless G3ID knows the team (`GET /teams/:id`). For `/api` requests it drops a session that belongs to another team's member (the app sees a signed-out request), refuses an Origin from another team's host, and sets `X-Team-Id`, `X-User-Id`, `X-Session-Type`, `X-User-Roles` after removing any a client sent. Apps don't use those headers yet (Phase 3); production app workers have `workers_dev = false`, so the gateway is the only way in.
- **Sign-in per team** (G3ID stays the sign-in app): each team signs in on its own G3ID, `<number>-id.<platform>` (G3: `1648-id.frcgearbox.com`). G3ID reads the team from the gateway's `X-Team-Id` (`requestTeamId()`, `workers/g3id/src/lib/team.ts`; the site's team without it) and sends members back to `teamFrontend()`. Google, GitHub and Steam all call back on the platform host `id.<platform>` (`signInCallbackApiUrl`; the gateway gives it no team), with the team, return address and any account being linked in the sign-in's state (`lib/oauth-state.ts`). Every sign-in method (providers, Slack codes, email, kiosk PIN) only signs in that team's members, and `sanitizeRedirect(url, team)` only allows that team's pages. Cross-team links in Slack DMs use `teamAppUrl(team, "id")`.
- Production deploys from GitHub Actions when a release lands on `public` (`release.yml` → `deploy.yml`, migrations first). By hand: `pnpm db:migrate:remote`, then `pnpm run deploy` (all) or `pnpm --filter @g3/worker-<app> run deploy` (`wrangler deploy --env production`; `[env.production.build]` in its `wrangler.toml` builds the app first). No Cloudflare Pages. See `docs/deploy.md`, including the one-time switch-over.

### Team-scoped apps (roadmap Phase 3)

- **The request's team is in `@g3/auth`.** `requireAuth` and the other middlewares set `c.get("teamId")`: the gateway's `X-Team-Id` (`TEAM_HEADER`, `requestTeamId()`), or the site's team without it (an app's own port in dev, tests). A session counts only on its own team's addresses (another team's member is signed out), so `teamId` is always the signed-in user's team. Who is signed in is still asked of G3ID, never taken from the gateway's `X-User-Id` alone.
- **Tenancy helpers, also in `@g3/auth`** (the roadmap's platform SDK; no separate package): `inTeam(table, teamId, ...conditions)` for every `where` on a team table, `withTeam(teamId, values)` for every insert into one, `teamMembers(env, teamId)` / `activeMembers` (G3ID's `/api/internal/teams/:id/members`, with `isAdmin`/`isMentor`; apps keep no list of people), `deleteTeamRows(db, teamId, tables)`, `sendMemberDM(env, teamId, userIds, text)` and `sendTeamMessage(env, teamId, channel, text)` (G3ID's `/api/internal/teams/:id/chat/dm-members` and `/chat/message` send them on the team's chat, Slack or Discord, with its own bot; the token never leaves G3ID; nothing is sent when the team has no chat; text is in Gearbox's chat format, see "Discord" below), `encryptSecret`/`decryptSecret` (AES-GCM with the worker's `SECRETS_KEY`, for a team's secrets kept in D1), and `forwardIdentity(c)` (cookie + `X-Team-Id`) for calling another app as the user. Orders' part lookup and Shop's printing use it to reach the member's own team's edge box.
- **Tenancy lint** (`pnpm lint:tenancy`, `scripts/tenancy-lint.ts`, in CI): for each team-scoped app listed in it, a Drizzle query on a team table without `inTeam`, an insert without `withTeam`, any raw `.prepare(`, or a `sql` template naming a team table fails. A query that must read every team's rows (a cron finding which teams to work on) goes right after a `// tenancy: all teams (<why>)` comment. Add an app (its dir and team tables) in the pull request that makes it team-scoped.
- **Isolation test** (`@g3/testing/isolation`, `checkIsolation({ app, seed, snapshot, bodies, skip })`): every team-scoped app has one (`test/isolation.test.ts`). It seeds teams A and B, calls every route of the exported Hono `app` as A's admin, mentor, student and kiosk session with B's ids, and fails if an answer contains a marker only B has or B's snapshot changes. It skips `/internal/*`, which only other workers reach.
- **Deleting a team's data:** every team-scoped app has `DELETE /internal/teams/:teamId` (`/api/internal`, which the gateway never answers), deleting all its rows with `deleteTeamRows(db, teamId, tables)` from `@g3/auth` (one batch, children first; Shop also its R2 prefix and Onshape webhook, Edge its box key and link, Orders its catalog-copied note). Each app's isolation test also runs `checkTeamDeletion` (A's data all gone, B's untouched, a second delete OK). A new team-scoped app adds the route, `delete: true` in its manifest, its binding on the platform and the test.

  - **The top bar** (`nav-bar.css`): surface, border, muted text for links, text for the current page.
  - **Scouting** (plain CSS, `apps/scouting/src/styles.css`): every brand color and gray is an expression over the `--g3-light-*` / `--g3-dark-*` variables that gives the old color on the defaults (a rule under `html[data-theme="dark"]` uses the dark ones, any other rule the light ones). Write new rules the same way.
  - **Attendance** is a Tailwind app; its QR code displays use the `--g3-*` variables and pin the dark theme (`forceTheme("dark")`), so they show the team's dark colors.
  - **What stays fixed:** colors that mean something (green for done or signing in, red for an error, deleting or signing out, amber for a warning, status badges, the red and blue alliances, chart ramps, other companies' logos). The platform's public pages belong to no team and keep the built-in colors.

The light accent is the brand color (`brandColor(settings)` in `@g3/site-config`): the primary palette (`--color-primary-50…900`, built in `packages/ui/src/team-ui.ts`) is built from it, and the app icons take it in both themes. In dark mode the palette's tints (50–300) are dark (the brand color sunk into the page), and its solid shades (500 and darker: buttons, selected tabs, focus rings) and brand text (`text-primary-*`) take the dark accent, which `packages/ui/src/theme.css` builds from `--g3-dark-accent`. So a theme's buttons are filled with that theme's accent (`fillColor(settings, mode)`). A team that keeps the default light accent gets `builtInBrandColor` (`#a32035`): the hand-tuned palette in `index.css` and the icons as drawn.

The sliders only ever change their own box, never its hue. The other palette colors are under "More options", closed by default (a field in it that can't be saved opens it), where each theme has a preview (`ThemePreview`): a small mock page using all seven of its colors, with the button in that theme's accent and button text.

- App icons follow the team's brand color (`packages/ui/src/team-icon.ts`). Each icon file is a black tile with a white drawing and one accent in the built-in brand color (`#a32035`); for a team with another brand color, the SVG is read in the browser and that accent swapped. `useTeamIcon(src)` / `<TeamIcon>` from `@g3/ui` do it for an icon on a page (the top bar's, the portal's tiles), and `applyTabIcons` (run with the rest of the appearance) for the page's own `<link>` icons: the tab's SVG, and its `.ico` fallback and home-screen icon redrawn as PNGs. The files don't change, a team with the default color gets them as they are, and the platform's own public page keeps the default. **A new app icon must use exactly that accent hex** to be recolored.
- **Installed apps** (Add to Home screen): each app's `public/manifest.webmanifest` (linked from its `index.html`; standalone, opens at `/`) lists `icon-192.png` and `icon-512.png` (the rounded tile) and `icon-maskable-512.png` (the tile's color edge to edge, the drawing inside the middle 80%), so Android fills its circle or squircle with the icon instead of putting a small square on white. They're fixed files in the built-in color, so an installed icon doesn't take a team's color. Portal's and the platform's are the Gearbox mark (black and red); ID has none, since it only signs people in. A new app adds all four.
- Portal resource links (public site, Slack, Discord, GitHub, Instagram, FRC-Events, The Blue Alliance, Statbotics, match13, FRCTools Orders and FRCBOM; the last two default to the same address for every team, `toolLinks` in `team-links.ts`) have editable HTTPS URLs and `hiddenLinks` controls. Hiding preserves the URL; removing clears it. Empty or hidden links are omitted, including the public-site link on ID's sign-in page.
- **Apps grid order** (Team Appearance, `appOrder`): every Portal tile's key (`PortalTileKey`: the team's apps in `portalAppLabels`, and its links), once each, in the team's order; admins drag them on the editor (`apps/portal/src/plugins/admin/app-order.tsx`, `@dnd-kit`). `completeAppOrder` fills in tiles a saved order doesn't name (one added later) in their default places, both when G3ID reads a stored record and on Portal; a stored record without one gets `defaultAppOrder`. G3ID rejects an order with a tile missing, repeated or unknown. Hidden or empty links keep their place but don't show. A new Portal tile needs a key in `portalAppLabels` or `teamUiLinkLabels` and a place in `defaultAppOrder`.
- Reset to defaults restores the editor form; Save applies it. Stored settings from older versions gain new link and setting defaults without resetting their branding or restoring explicitly empty links. Current writes require the full schema.

### Shared navbar and light/dark mode

- Every app's top bar is `AppNavBar` from `@g3/ui` (`packages/ui/src/components/app-nav-bar.tsx`, styled by its own plain CSS in `nav-bar.css` so it renders the same in Scouting, which doesn't use the shared Tailwind theme). Each app's `shared/nav-bar.tsx` is a thin wrapper: it filters pages by permission, marks the current one (`activePath`: the most specific link covering the URL), and passes react-router links via `linkWith(Link)`. The menu button (top left) is there at every width and opens a drawer: under the heading "All Apps", the team's home ("Portal") and then its apps that are on, in the order of the home's grid, with the one you're in marked. Below 768px the pages move into the drawer too, above the apps and a dividing line; above it they stay across the bar, and the drawer is only the apps. There is no separate All Apps link.
- **Who's signed in and which apps are on** come from `packages/ui/src/session.ts`, asked once per page load and shared: `useSignedInUser()` (G3ID's `/auth/me` through `apiPath("id")`) and `useTeamApps()` (the platform's `/team/apps`; "all" when it can't say). The bar greets the user ("Hello, <name>!", a link to the Account page on Portal) at its right end at every width, on a phone too, where the bar's other controls are in the drawer; a name that doesn't fit is cut short with "…". Never for a kiosk PIN session. `AppNavBar`'s props: `allApps={false}` for no app list (Shop's kiosk mode), `account={false}` for no greeting (the same), `team={false}` for the platform's own pages, which belong to no team (the operators' console: built-in colors and icon, no team name, app list or greeting, nothing asked of ID), and `signedIn` for an app that signs people in and out without reloading (ID passes what it knows, so the bar follows). An app passes `actions` only for controls of its own (Portal's Sign in, Shop's kiosk badge).
- Light/dark is one setting for all apps: the `g3_theme` cookie on `.g3robotics.com` (shared across ports on localhost), applied as `html[data-theme]` before first paint by a small script in each app's `index.html`; `useTheme`/`setTheme` (`packages/ui/src/theme.ts`) change it, and open tabs pick up a change on focus. No cookie → the system setting.
- One color scheme for every app (`packages/ui/src/colors.css`): page `#f4f6f7` / dark `#171717`, surface (cards, top bar) `#ffffff` / `#262626`, inset `#eef1f3` / `#1e1e1e`, line, text, muted and accent, as `--g3-*` CSS variables that switch with the theme. Those are the defaults; a team's own colors (Team Appearance) replace them at runtime. Tailwind apps use them as `bg-page`, `bg-surface`, `bg-inset`, `border-line`; every page's root background is `bg-page` and every card's `bg-surface`. `--g3-brand` is the team's color for solid fills (the showing theme's accent, so the same as `--g3-accent`) and `--g3-on-brand` the text on them (the team's button text color for the showing theme); `--g3-light-*` and `--g3-dark-*` are both themes' colors whichever is showing, for a rule written for one theme.
- Apps are styled light. Dark mode comes from `packages/ui/src/theme.css` + `theme-palette.css`: neutral ramps (secondary, gray, slate, ...) invert onto the dark palette's colors, tinted backgrounds (`*-50..300`) become dark tints, and dark text shades (`text-*-600..950`) become light. Solid fills (`bg-*-500/600`) are unchanged, except the team's own (`bg-primary-500` and darker), which take the dark accent. So write light-mode classes; use a hex value (`bg-[#24292f]`) only for a color that must not change in dark mode, and never for the team's color or a gray.

### Color Implementation

The built-in colors are in `packages/ui/src/index.css`'s `@theme` block and `colors.css`; a team's own replace them at runtime (see "Editable team appearance"):
- Primary palette (the team's color; burgundy by default): primary-50 through primary-900
- Secondary palette (neutral grays, from the team's text, muted, border and inset colors): secondary-50 through secondary-900
- Used across all apps via Tailwind classes
- **Do not use hardcoded colors**, and don't use a Tailwind color like `red` or `blue` as an accent: use `primary-*`, `secondary-*`, `bg-surface`, `bg-page`, `bg-inset` and `border-line`, and `text-on-primary` for text on a solid `primary` fill. Red, green, amber and the like are for meaning only (an error, deleting, done, a warning)

### Database Schema

Key tables in D1:
- `teams` — each team, keyed by `frc<number>` (`teamKey`). G3ID doesn't read the gateway's `X-Team-Id` yet (sign-in per team is roadmap 2.5), so the rows it creates are for the team in site.ts (`currentTeamId()` in `workers/g3id/src/lib/team.ts`)
- `core_users` — user accounts with status (pending/active/rejected); **each belongs to exactly one team** (`team_id`, no memberships table; roles stay as `is_admin`/`is_mentor`)
- `core_user_identities` — linked auth providers per user
- `core_sessions` — active sessions (deprecated in favor of KV)
- `core_user_pins` — 3-digit PINs for kiosk login, unique within a team; a kiosk signs in only its own team's members
- `kiosk_devices` — registered shop devices with tokens, in the activating admin's team
- `kiosk_activation_codes` — 6-digit codes for device activation (30-min expiry)
- `core_slack_link_codes` — Slack sign-in and link codes with polling status: 4 digits, unique within a team (migration 0015); `insertCode` in `lib/slack-code.ts` deletes codes a day after they expire and draws again if a code is taken

Migrations are SQL files in `workers/g3id/src/db/migrations/` — always add new migrations for schema changes.

### Slack Integration

Three flows:
1. **Sign-in**: User runs `/signin 123456` with a code from the web app
2. **Link**: Authenticated user runs `/link 123456` to add Slack to their account
3. **Events**: Slack bot receives 4-digit codes via DM and processes them

Routes:
- `POST /slack/events` — Slack event API (URL verification, DM messages)
- `POST /slack/commands/signin` — `/signin` slash command
- `POST /slack/commands/link` — `/link` slash command
- `GET /auth/slack/initiate` — Start sign-in flow
- `GET /auth/slack/link` — Start linking flow
- `GET /auth/slack/status` — Poll for completion (frontend calls every 2s)

Rate limiting: 5 attempts per 15 minutes per Slack user (via KV).

**New members waiting for approval:** a Slack or Discord sign-up that isn't a team's first member makes a pending account, and every active admin of the team with its chat linked gets a DM with the person's name, email and a link to their page on Portal's Members list (`dmAdmins` in `workers/g3id/src/lib/member-dm.ts`, called from `handleSlackCode` in `lib/slack-code.ts` and `signInWithDiscord` in `lib/discord-sign-in.ts`). It never fails the sign-up. Slack and Discord sign-ups are the only ways to make a pending account.

**Choosing a channel:** every page that asks for a channel uses `ChannelPicker` from `@g3/ui` (plain CSS, `channel-picker.css`): admins search the team's channels by name on its chat (G3ID's `GET /admin/chat/channels`: Slack's from `listChannels` in `@g3/slack`, which needs the bot's `channels:read` and `groups:read`; Discord's from `listChannels` in `@g3/discord`, with whether the bot can post worked out from its roles and the channel's overwrites), it saves the channel's ID and warns when the bot can't post there. Without a chat, or on a Slack connection from before those scopes (409 `reconnect`), it links to Integrations and takes a typed ID. Used by Shop's channel settings and Portal's Notifications page. Pages name the team's chat with `useTeamChat()` / `chatName()` from `@g3/ui` (G3ID's public `GET /team/chat`).

**Slack per team:** one Slack app, installed into each team's workspace by a team admin (the Slack card on the Integrations page of the team's admin pages, Portal's `/admin/integrations`: G3ID's `GET /slack/install` through `/api/~id`; Slack calls back on `id.<platform>/api/slack/oauth/callback`, which sends the admin back to the home's `/admin/integrations`; the old `/admin/slack` redirects there). `slack_installations` holds each team's workspace ID and bot token, encrypted with the `SECRETS_KEY` secret (`encryptSecret` in `@g3/auth`). `lib/slack-install.ts`: `slackForTeam(env, team)` gives the workspace and a `{ SLACK_BOT_TOKEN }` for `@g3/slack`; `teamForWorkspace(env, workspaceId)` routes slash commands and events. A sign-in code only works from its own team's workspace. The site's team falls back to the `SLACK_BOT_TOKEN` / `SLACK_TEAM_ID` settings until it connects. Every app sends its messages through G3ID (`sendMemberDM`, `sendTeamMessage`, `/chat/*`), which sends them on Slack or Discord; no app holds a chat token.

### Kiosk System (Shop Devices)

PIN-based access for untrusted computers:
- 3-digit numeric PIN assigned per user
- Device activation via 6-digit code (admin-generated, 30-min expiry)
- Kiosk token stored in browser localStorage, validated on every request
- Sessions marked as `sessionType: 'pin'` to prevent admin access
- If token is invalid/revoked, app redirects to `/kiosk/activate`

**Worker tests** (`pnpm --filter @g3/worker-orders test`, or `pnpm test` for everything; CI runs them on every PR):
- Every worker has `vitest.config.mts` (`.mts`: the Workers test pool needs ESM) built by `workerTestConfig` from `packages/testing` (`@g3/testing`). Tests run inside the Workers runtime via `@cloudflare/vitest-pool-workers` (pinned in the pnpm catalog: Vitest 4.1.x only) against local D1/KV/R2 from the worker's wrangler config, with its D1 migrations applied before each test file (`packages/testing/src/setup.ts`). No Cloudflare account or secrets: `remoteBindings` is off, and tests must not rely on `.dev.vars`.
- Storage is per test file, shared by the tests in a file, so each test makes its own records (random URLs, generated PINs) instead of assuming an empty database.
- Test users have a team (`teamId`, the site's by default); `teamUsers(teamId)` gives the standard users in another team with ids of their own, and `asUser`/`callAs` send `X-Team-Id` like the gateway. The G3ID stub answers per team, including `/internal/teams/:id/members`.
- Other workers are stubbed: `G3ID` is a stub that answers `/auth/me` for the user in a test cookie (never admin/mentor for a `pin` session, like the real one), and other services (e.g. `EDGE`) can be `offlineService`. In tests, `callAs(student, "/path", { method, body })` / `jsonAs(...)` from `@g3/testing/worker` sign requests in as the users in `@g3/testing/users` (`student`, `otherStudent`, `mentor`, `admin`, `kioskAdmin`).
- G3ID itself is tested for real (`workers/g3id/test`): users and sessions are seeded with its own helpers (`createUser`, `sessionCookie`, `createUserWithPin`, `activateKiosk`).
- Attendance's records are in its own D1 database (`ATTENDANCE_DB`); `workers/attendance/test/attendance-d1.test.ts` covers sign-in/out, hours, auto-closed sessions and admin actions against it.

**Discord** (`docs/roadmap/discord.md`, set up in `docs/deploy.md`, "Discord"): a team uses Slack or Discord, one at a time (`saveInstallation` and `saveDiscordInstallation` refuse the second). One Discord app with one bot token (`DISCORD_BOT_TOKEN`, with `DISCORD_CLIENT_ID`/`DISCORD_CLIENT_SECRET`; required: Discord is always offered) serves every team, so `discord_installations` (G3ID migration `0019`) holds only each team's server id (`lib/discord-install.ts`). Everything is plain HTTPS (`@g3/discord`): no Gateway connection, so the bot never reads messages. Admins connect a server on Integrations (`GET /auth/discord/install`, which also links their Discord); members sign in, sign up and link with Discord's OAuth (`routes/auth/discord.ts`, one callback, `/auth/discord/callback` on `id.<platform>`, `DISCORD_REDIRECT_URI` for the site team in dev): someone new is signed up only if the bot finds them in the team's server and Discord has verified their email (`lib/discord-sign-in.ts`). `lib/chat.ts` is the one place that sends: `chatForTeam` (Discord first, else Slack), `sendChatDM`, `postToChannel`, `listChatChannels`; a Discord send that fails because the bot left the server forgets the team's server. Messages are written in **Gearbox's chat format**, Discord's Markdown that both can show (`**bold**`, `[label](https://...)`, `> ` quotes, `<t:UNIX:f>` times, Unicode emoji, never `:names:`); Discord takes it as it is (in 2,000-character pieces, `splitMessage`) and Slack gets `toSlack` from `@g3/slack`. The fake `discord.com` for worker tests is `@g3/testing/discord` (ids say who's in which server).

**Test Slack locally:**
- Sign-in codes generated and stored in D1
- Frontend polls `/auth/slack/status` every 2s
- Status persists in D1 (immediate, not KV eventual consistency)

**Test kiosk flow:**
- Admin generates 6-digit activation code
- Device enters code at `/kiosk/activate`
- Receives kiosk token, stores in localStorage
